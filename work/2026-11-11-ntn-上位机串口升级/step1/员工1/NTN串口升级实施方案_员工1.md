# NTN 串口升级实施方案

作者：员工1  
日期：2026-11-11  
更新：2026-11-28
版本：V1.1 方案稿，尚未实装。适用范围：PC通过本板主MCU的现有串口升级MS150/ST1000模组自身。

依据和已知限制见 [可行性与工作报告](NTN串口升级可行性与工作报告_员工1.md)、[协议核对](协议核对与参考工具分析_员工1.md)。本方案中的PC会话帧、接口名、超时初值均为本项目新增设计，不是厂商现有协议。

## 1. 架构与实施范围

```text
Windows升级工具
  文件解包/四组件清单校验/LogMap保留/备份文件/会话记录
        │ 现有PC RS232链路，独立波特率（初期115200 8N1）
主MCU upgrade_service
  收包会话 → 外部NOR整包暂存/校验 → READY → 安装会话
  安装会话 + 4KiB块缓存 + MS150下载状态机 + GPIO控制
        │ USART3 PB4 TX / PB5 RX，115200握手，按profile切1.5M
U22电平转换
        │ 模组UART0
MS150/ST1000 ROM下载器 → 模组Flash E31/DSP/分区表
```

2026-11-28功能目标更新为二级Boot、E31、DSP、NV四组件，外部NOR完整暂存是主路径。先以E31＋DSP验证传输和恢复，再完成Boot及NV专项，不能提前宣称四项交付。NV XML需转换，LogMap留PC；不整片擦除、不处理卫星下载。本项目模组升级不会改义现有主MCU OTA。

完整缓存分区、状态和断线恢复以 [外部Flash暂存方案](NTN固件外部Flash暂存方案_员工1_V1.0_20261128.md) 为当前设计。以下串口帧是内部提案，不是已冻结接口；BEGIN需明确STAGED_FULL或显式STREAM_FULL模式，禁止悄悄降级。

当前源码已有主MCU OTA，`NTN_OTA_APP` 构建提供PC_FULL/YMODEM入口。本方案不改它的协议含义；两种升级会话必须互斥，并共用清晰的UART1维护所有权，不能同时启动YMODEM和MS150代理。

上位机宜使用现有PC工程框架，升级引擎与界面分离；如果现有Web Serial链路无法可靠保持长时独占，可提供独立Windows串口工具。不得把生产串口当调试控制台输出日志。MCDT作为基准工具和救援参考，原样直接透过当前AT模式不构成实施方案。

另一条救援路线是PC TTL串口直连模组UART0，用外部方式控制BOOT/RESET；需硬件人员确认接线点、电平及隔离MCU驱动，避免两路发送端并联。不能把RS232电气信号直接接入模组TTL脚。

## 2. MCU改动边界

| 位置 | 必须改动 | 完成判据 |
| --- | --- | --- |
| `ntn_ms150.c/.h` | 增加NORMAL/UPGRADE/RECOVERY所有权状态；统一切换收发路由 | 同一时刻一个UART读者、一个授权发送者 |
| `hw_power.c/.h` | 增加enter_download/exit_download；进入函数保持PA10=1；普通上电、复位入口在升级中返回BUSY | 不再因既有power-on函数清除BOOT |
| `mcu_local_cmd.c`及PC串口入口 | 新增模组升级能力、维护入口、状态查询；进入后专用二进制帧解析 | 任意00/CR/LF/AT样式镜像不会被本地AT解释 |
| 新增 `ms150_download.c/.h` | 封装命令编解码、XOR、读页、擦除、变长写、ACK及超时 | 可在内存串口替身中独立验证 |
| 新增或扩展 `upgrade_service` | 串联块缓存、会话、持久状态、进度和错误恢复 | 对PC区分接收完成与写入读回完成 |
| 参数/状态持久层 | 独立的模组升级未完成标志，具备原子保存和坏记录处理 | MCU复位后在NTN业务初始化前进入恢复模式 |
| 驱动/配置 | 改速及TX_CPLT硬件排空；RX错误可见；必要时DMA | 1.5M收发完整，实测波特率符合链路误差预算 |

不要复制一份AT/串口服务，也不要用独立线程抢读设备。UART接收入口先检查所有权：升级时只交下载状态机，正常时继续现有AT/URC/透传。切换前等在途AT结束，超时则明确失败，不能把一半AT响应误当ROM ACK。

维护期间暂停自动建链、定位AT、上报、蓝牙原始AT和PC普通透传。电源管理、看门狗及线程心跳继续工作；禁止休眠和无关模组复位。原有60秒调试锁不可代替升级会话锁，因为升级可能持续数分钟且不能超时自动恢复业务。

暂停业务指业务动作停止，不是直接永久挂起受task_wdt监控的线程。需定义维护态心跳或成对暂停/恢复监控机制，同时保障OTA BL1启动的SWDT继续被正确服务；超时常量以当前注册和构建为准，不复制其他报告的线程超时数字。

模块升级期间RS232作为升级专用口：在业务边界上明确停止外部RAW输入，已经缓存的业务保持原有顺序；队列满时按既有策略报告，不静默清除。

## 3. GPIO启动状态与复位恢复

| 状态 | PB15 电源 | PA10 BOOT | PA8 RESET | 行为 |
| --- | --- | --- | --- | --- |
| 正常运行 | 1 | 0 | 0 | 模组从Flash正常启动 |
| 进入下载前 | 1 | 1 | 1 | 模组BOOTSEL低，RESETN低 |
| ROM下载 | 1 | 1 | 0 | 模组复位释放，115200输出U |
| 正常启动前 | 1 | 0 | 1→0 | 释放BOOT并产生复位脉冲 |
| 擦写失败/PC断线 | 1（供电允许时） | 1 | 0 | 保持下载状态等待恢复，不交还AT业务 |

从断电状态进入时：先配置安全GPIO并保持RESET，选好BOOT后再使能主电源；测量VDDIO_AON稳定后释放RESET。不要在掉电模组输入脚强驱动造成反向供电。PA15唤醒按本工程已验证电平处理，不根据旧GPIO表注释擅自反转。

在第一次破坏性擦除之前原子保存 `modem_upgrade_incomplete=true`，记录机型、发布清单hash、目标版本，不把每一页进度反复写MCU片内Flash。启动时 **早于普通NTN上电与自动复位** 检查该标志：有标志则走下载恢复路径；硬件初始态和普通电源函数也须配合，避免先运行不完整模组再补救。

标志只在目标版本查询和自检成功后清除。若最终查询完成但清标志时MCU复位，下次可先以只读验证确认目标镜像后完成收尾，不能直接宣布失败重刷全部。持久记录损坏时进入明确的人工维护状态，不自动擦写。

## 4. PC与MCU维护会话（新增提案）

能力查询使用独立标识，例如 `AT+MCUNTNUPG?` 返回协议版本、支持机型、最大帧/块、可选下载profile及阶段能力。写入口名称和应答格式由PC/MCU共同冻结。现有 `AT+MCUUPG?` 含义保持为主MCU升级，不能静默改义；OTA构建中它已为supported=true，不能据此自动进入MS150升级。

文字维护入口只用于切换模式；MCU先回完整的READY应答并排空发送，PC再发二进制HELLO。进入后停止普通AT及本地命令解析。退出必须通过会话终结状态，不能通过在镜像字节流里搜索 `+++` 或 `AT`。

建议二进制帧：

| 字段 | 字节数 | 定义 |
| --- | ---: | --- |
| magic | 4 | 固定ASCII `NUPG`，只用于帧同步 |
| version | 1 | 1 |
| type | 1 | 下表消息类型 |
| flags | 2 | 大端；首版仅0，未知置位拒绝 |
| session_id | 4 | 大端；每次会话生成的新ID |
| sequence | 4 | 大端；从1递增，不允许回绕 |
| payload_length | 2 | 大端，0～1024 |
| payload | 0～1024 | 消息数据，多字节整数大端 |
| crc32 | 4 | 大端保存CRC-32/ISO-HDLC，覆盖version至payload末尾；与Python zlib.crc32结果一致 |

固定开销22 B，最大1046 B。magic出现在payload中是普通数据，不转义；按已校验长度收取。长度超限、版本不支持、CRC错误均不得产生擦写或GPIO副作用。CRC错误可丢弃候选帧并继续限量扫描magic，设置帧间/全帧超时防止永远等待坏长度。CRC用于传输检错，不提供认证。

| type（拟定） | 消息 | 核心内容/响应 |
| --- | --- | --- |
| 0x01 | HELLO/STATUS | 版本、能力、当前会话状态、上次错误、下一块偏移 |
| 0x02 | BEGIN | 经PC校验的发布清单、E31/DSP大小/hash、目标机型/profile；拒绝未知组合 |
| 0x03 | GET_BACKUP | 按白名单读区导出原始数据，响应含分区及偏移 |
| 0x04 | BLOCK_BEGIN | image_id、分区内偏移、实际块长度、块CRC32；申请唯一4KiB缓冲 |
| 0x05 | BLOCK_DATA | 块内偏移＋最多1020 B数据；按偏移去重，不允许越界或重叠冲突 |
| 0x06 | BLOCK_COMMIT | STAGED_FULL下提交缓存NOR块，读回后才回STORED；不擦MS150 |
| 0x07 | FINISH_CACHE | 完整缓存及清单/转换产物校验通过，标READY，不立即安装 |
| 0x08 | ABORT | 首次擦除前允许安全退出；之后进入RECOVERY_REQUIRED，不自动运行 |
| 0x09 | INSTALL | 独立启动已验证缓存的四组件安装，最终查询版本/配置后完成 |
| 0x80 | ACK | 回显session/sequence、阶段和结果；区分RECEIVED、STORED、READY和TARGET_VERIFIED |
| 0x81 | ERROR | 错误码、image_id、块地址、MS150原始响应摘要 |

数据帧使用最多1020 B载荷数据，预留4 B块内偏移；末帧可短。BEGIN过大时用独立有界清单传输，不能突破帧长或在栈上临时分配整个JSON。只接受固定schema，不直接信任上位机给出的任意物理Flash地址。

PC一次只保持一条控制请求在途。相同session/sequence与相同内容重发，MCU返回缓存结果；相同序号不同内容返回冲突。COMMIT应保存“执行中/已完成”的阶段，ACK丢失后不得把已执行的擦除无条件再做一遍。状态查询用新序号查询，不掩盖旧事务结果。

软件复位后RAM缓存丢失，PC会话日志只作恢复提示；重新读取目标，确认清单hash一致、分区表和boot可识别后，比较目标块内容。已一致的块可跳过，不一致的块重新完整接收→整扇区擦除→重写→读回，不直接从上次字节位置续写。进度记录不能代替Flash内容验证。

## 5. MS150下载状态机

```text
IDLE → PRECHECK → RECEIVE_CACHE → VERIFY_CACHE → READY
     → INSTALL_REQUEST → EXCLUSIVE → ENTER_ROM → SYNC
     → FLASH_INIT → READ_AND_BACKUP → ERASE_WRITE_VERIFY
     → VERIFY_ALL → COMMIT_TABLE → RUN_AND_PROBE → COMPLETE
任意失败 → ERROR → RECOVERY_REQUIRED（破坏性擦除之后）
```

### 5.1 进入ROM与初始化

1. 拒绝电源不足、其他升级/维护在途、机型或包不匹配的请求。PC完成整包来源/完整性校验，显示将升级MS150而非主MCU。
2. 暂停业务，接管串口及GPIO，记录当前PC/模组波特率和待恢复状态。
3. 按上一节拉BOOT/RESET，UART3使用115200 8N1并清残留。等待连续U（建议初值至少3个，最终按实测固化）。超时不发送擦除指令。
4. 按厂商流程发 `C0 3F`，处理停止U后的残留；版本返回仅诊断，不作为成功ACK。再发 `46 B9`，必须得到0x06。
5. 发送清写保护寄存器命令。原工具两次调用均为mode7（累计至少2 B），不是通用06 ACK；先由CAP02抓取实际完整文本/ACK、结束边界和错误分支，再冻结解析器。仅有2 B数据不足以判协议成功。
6. 改速由一个profile接口统一发起，避免外层55 AA和内部前置55重复。已核对的MCDT函数仅在目标57600时跳过前置55，其余目标走该路径；1.5M目标发送50 09 A6，mode8收首字节06后，每次本地串口改速尝试前Sleep500ms，最多5次本地配置。这个静态行为是兼容参考，不等于ROM要求精确500ms；实际ACK速率和允许等待窗口由CAP03确认。PC→MCU波特率不随之改变，不能因本地配置失败盲目重发50。

115200慢速烧写只有在厂商确认/样机验证后才成为可选profile；不能假定略过文档的高速切换就一定可用。初次bring-up可先完成115200只读探测。

### 5.2 读表与备份

先用 `EB + BE32(addr) + XOR` 读取首个256 B。校验两magic、结构版本、容量及所有被用到的分区地址，限制到项目白名单；遇到工具新版结构或未知product直接拒绝写入。

不能仅读取20 B，也不能把256 B页当完整4KiB扇区备份。首扇区按16页读取保存到PC，校验hash，并保存工具profile、当前ATI/CGMR、模组身份、boot/NV兼容记录。NV/设备专属参数按经确认的真实分区备份，日志不明文展开敏感身份。

对旧式256 B T_Header，结构推导的fixed_inf长度为0x58，E31三元组位于0x70、mv_length位于0x78，DSP0 code三元组位于0x7C、mv_length位于0x84。**这些偏移只用于已验证的旧布局**；目标结构不一致不能继续套用。采用显式字节读写及边界断言，不直接把未对齐字节强转C结构。

### 5.3 4KiB块擦写与读回

以下是MS150安装阶段：数据从已验证的外部NOR供给。每个完整块以目标分区内4KiB边界开始，末块允许短于4KiB；写起始地址同时256 B对齐。块长≤4096，不要求整个64KiB驻留RAM。在线流式模式如保留，另行声明PC持续在线要求。

```text
MCU从外部NOR读取完整块 → 验证长度/偏移/块校验 → 写入允许范围校验
→ 擦除20 + BE32(sector_addr) + CHK，等ACK
→ 发7A + BE32(page_addr) + BE32(actual_len)
→ 等待至少30ms → 发送完整缓存数据 + 整帧XOR
→ 等写完成ACK → 按256B页读回覆盖全部实际数据
→ MCU逐字节比对 → 回PC VERIFIED，再处理下一块
```

擦除范围向4KiB上取整，但不得超出当前分区。末块只发送真实长度，mv_length不加对齐填充；读回末页时只比较有效范围，额外字节按未使用尾部处理。未获厂家确认前，不使用可能覆盖相邻分区的整片或额外DSP擦除选项。

0x06须按当前状态理解：只有对应本次命令的响应才能推进状态。残留U、ASCII状态、延迟的旧ACK与读回数据必须分开，不可以“收到任意字节就成功”。读页固定收256 B，不能把数据中的0x06当ACK。

写超时存在“写成功但ACK丢失”的可能。先停止发送并重新同步，读回判断；若下载器仍在等数据导致无法同步，硬复位重入ROM后重新初始化。恢复不确定块时先收齐完整扇区数据，再擦除重写。CRC/XOR错不能直接在原Flash上叠写重试。

对同一session清单hash固定，MCU拒绝变更镜像、跳块、跨分区和长度漂移。MCU在缓存READY前全量读回NOR计算hash，安装时对目标读回再核验；初版可由PC独立复算目标读回作交叉验证，量产版MCU本地hash实现需单独验证。

### 5.4 分区表最后提交与启动

E31、DSP都读回一致后，基于原首扇区副本仅修改已确认的mv_length：CA034 E31=0x2649D7、DSP=0x12317。保留fixed_inf、NV、文件系统等未知/未更新字段及首扇区其余页。

擦除首扇区后，将修改后的256 B表页和需要保留的其余页写回、读回核对。厂商文档给出的表页写命令是 `32 + BE32(0) + DATA_256 + CHK`，其余保留页采用已确认的页写命令。未验证命令及页行为前不执行此阶段。只备份第一页然后擦4KiB、丢弃其余页不是保留。

该过程仍有首扇区擦写窗口，不具备原子A/B提交保证。默认方案通过保持ROM可进入及PC备份实现重刷恢复；如产品要求无人值守断电自动回滚，必须增加厂家支持的双槽/安装记录/启动验证机制，另立验收项。

正常收尾按profile发 `50 04 AB` 恢复模组UART115200；然后PA10=0、PA8复位脉冲。硬件启动优先，因为恢复BOOT电平更明确。`B0 4F`只作为经过验证的可选软件启动，不掩盖BOOT一直有效的问题。

等启动完成，查询ATI或AT+CGMR，检查目标版本，并执行基本AT、身份/NV保持及原有业务自检。若要求卫星入网，单列受天线、SIM、网络影响的实网结果；不能只用入网失败判断Flash写入失败，也不能仅见RDY就宣布整机业务正常。

### 5.5 二级Boot与NV完整profile

Boot默认参考范围0x8000起、容量0x20000，当前BIN为0x1DEFE；必须按目标结构确认并验证ROM重刷恢复，保持fixed_inf的sec_addr/sec_mv_length等固定含义。UI勾选不等于已经证明该设备允许更新Boot。

NV文档3.3节已给主/备分页指导；本次静态路径进一步确认02固定256 B页、尾页零填充、普通备份地址＋0x2000。当前XML候选为423 B、PageCRC偏移422、值42，主副本各两页。它仍需与MCDT实际线上页比较，不能直接作为已认证BIN。详见 [NV烧录核查](NV烧录文档与反汇编核查_员工1_20261128.md)。

完整profile必须在缓存中具备Boot/E31/DSP及经验证的NV二进制，且原始XML和转换产物hash对应。NV需保留设备专属参数，更新前保存原NV全区。任一组件尚未验证则能力查询明确不支持该完整profile，不能以E31/DSP成功返回四组件成功。

## 6. 资源、超时与日志

4KiB镜像块缓存必须用固定对象/受控堆分配，不放在线程栈。预计新增：块缓存4096 B、PC帧缓冲约1046 B、读回页256 B、状态及摘要约数百B，另有线程栈和驱动缓存；建议初步总预算8～12KiB，最终以map、堆峰值及栈高水位验证。可复用维护专用缓冲避免与业务峰值叠加，但不能静默共享正在使用的内存。

整包暂存如另行实现，OTA构建必须避开0x200000的scratch和0x210000/0x211000的日志扇区。现行reserved起点为0x212000；从0x200000分配会覆盖主MCU OTA数据。非OTA构建另有旧布局，依据构建ID/真实分区选择，不能只按Flash总容量猜地址。

超时分层：PC帧间/全帧超时、供数超时、ROM握手超时、擦除超时、块写超时、启动超时，分别配置。块超时至少包含 `30ms + (头+数据+校验)*10/baud + Flash编程时间 + 调度余量`。初值应保守且记录实测，原工具通用接收存在3秒等待不意味着所有擦除都应固定3秒。

每个等待保持看门狗心跳，禁止长时间关中断；等待PC数据时还未向ROM发写头，所以不会让ROM长时间等剩余数据。不能先发64KiB写头，再用115200慢链路逐段向1.5M模组“边收边发”。

发完头部后先等待USART_FLAG_TX_CPLT，再计时30ms；`rt_device_write()`或putc返回仅代表驱动接收/寄存器可写，不能视为物理线发完。改速和GPIO复位前同样排空发送。等待必须带绝对deadline和心跳，不能无期限忙等。

日志记录会话ID、工具/MCU版本、清单hash、设备匿名标识、profile、源/目标版本、阶段、分区/偏移、累计验证字节、错误和重试次数、备份路径。日志从维护应答通道或独立调试口输出，不能混入模组下载字节流。

## 7. 故障处理矩阵

| 失败点 | 处理 | 是否允许直接恢复业务 |
| --- | --- | --- |
| 包/hash/机型不符，尚未进入ROM | 拒绝，说明具体字段 | 是 |
| 无连续U/初始化失败，尚未擦除 | 停止，保留诊断；确认原镜像完整后正常启动 | 经状态确认可恢复 |
| PC帧CRC错/重复帧 | 不执行副作用；请求重发或回缓存结果 | 不释放维护锁 |
| 供数掉线，尚未擦除当前块 | 保持ROM，等待重连；已有写入则记恢复态 | 首次擦除之后不允许 |
| 擦除/写ACK丢失 | 同步或重入ROM，读回后决定跳过或整扇区重写 | 否 |
| 写入后读回不一致 | 有限次数整扇区重写；达到次数上限停止 | 否 |
| MCU复位/掉电 | 启动读取未完成标志，保持/重入ROM，PC恢复供数 | 否 |
| 首扇区写表失败 | 使用已保存完整扇区恢复，或ROM全流程重刷 | 否 |
| 新版本不能启动/版本不符 | 进入ROM，用已知兼容整包重刷；不宣称模组自动回滚 | 否 |

## 9. 开发前需要冻结的具体事项

1. 厂商/样机确认ROM读回是否固定256B、ACK在改速前还是改速后发出、页写0x02/表写0x32的确切时序，以及可安全用于试验的Flash区域。
2. 从目标读回确认旧T_Header还是其他分区格式，boot版本及CA033→CA034是否要求额外迁移。未确认前默认只读。
3. NV序列化、备份地址冲突与自动回滚能力由厂商明确；首版通过“不修改boot/NV、保留ROM恢复”控制范围。
4. 实板确认外置NOR容量和维护供电条件；整包暂存、长期无人值守升级不作为首版流式代理的隐含能力。

上述事项影响执行参数或生产可靠性，不改变“现有UART与GPIO硬件路径可用于升级”的资料结论。

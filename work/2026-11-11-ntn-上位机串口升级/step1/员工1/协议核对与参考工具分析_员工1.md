## 1. 工具身份与方法边界

EXE大小5,320,192 B，PE Machine=0x8664，ImageBase=0x140000000。准确SHA-256见 [mcdt_xrefs.json](evidence/mcdt_xrefs.json) 和 [source_manifest.json](evidence/source_manifest.json)。下文地址为该EXE默认映像基址下的VA，实际运行若ASLR重定位，应用RVA定位。

`inspect_mcdt.py` 用pefile读取节、异常函数表，用capstone查RIP相对字符串引用，再输出相关函数。字符串只说明程序包含某项功能；本分析进一步追踪实际构造指令、调用和接收分支。只有明确检查过的路径用于补正协议，不推断所有产品类型都走同一分支。

本次发现工具包含旧版/新版分区处理及多产品路径。因此把默认地址作为参考，把目标读回结构作为烧录依据。

## 3. EB读命令的文档错误

《MS150下载流程》Rev1.4第8页把 `EB 00 00 00 00 14` 解释为读取0x14(20)字节，和整页分区表需求冲突。

静态证据链：

1. VA0x14015F9A2写入EB，后续构造长度为5的命令本体，只有EB＋4字节地址，没有额外长度字段。
2. 公共助手的校验标志为1，初始FF逐字节XOR。对地址0，FF XOR EB = 14，追加后得到六字节帧。
3. 页读函数使用接收模式6。接收函数先对模式减6，经0x13DF64字节表、0x13DF3C跳转表，模式6落到0x14013DD68，要求累计字节数为0x100。
4. VA0x140166E00起的循环复制两组128字节，总计256字节；指定地址路径也相同。

因此，对这个工具版本，**14是校验，EB页读返回256 B**。实施时仍需验证目标ROM响应，不能把旧文档中的“20 B”照抄进读取长度。

## 4. 7A写命令、端序与节拍

VA0x14015D5EF先把操作码设为79，地址经BE32助手写入。VA0x14015D727取实际块长度，比较0x10000，小于该值时VA0x14015D732改为7A，并在头偏移5、6、7、8依次写入长度的高24、高16、高8、低8位。此时头长度由5改为9。

得到：

```text
79 + address_be32 + data_65536 + XOR
7A + address_be32 + length_be32 + data_length + XOR
```

上述XOR覆盖操作码、地址、长度（7A有）、数据所有字节，初值FF；最后加校验，整帧所有字节再XOR应为FF。`CHK`不是CRC-16/CRC-32，也不只计算数据。

VA0x14015D94C～0x14015D961先发送头。随后等待到时间差超过0x1C9C380，即30,000,000ns，再发送余下数据和校验，符合文档30ms要求。原工具后续按0x200字节拆分发送，这是主机写串口分段，不意味着模组每512 B有一次协议ACK。MCU实现可以按驱动容量分次写，但不能凭此增加不存在的ACK或省略最终整帧校验。

Flash表的uint32字段用小端读取，命令中的地址/长度用大端。这是不同层次，不能统一套用“全部大端”。表页序列化应显式指定结构版本和字节布局。

## 6. 分区、NV和二级boot的边界

旧T_Header结构按文档字段及4字节对齐推导：fixed_inf=88 B（0x58），随后各partition_t=12 B，总表256 B；E31.mv_length在0x78，DSP0.mv_length在0x84。该推导只服务于已识别的旧结构。工具还含其他分区结构的字段字符串，不能把同一EXE里出现的新表字段混入旧表。

`fixed_inf.sec_mv_length=0x2000` 表示启动搬移长度，不能用122,622 B的boot文件大小替换。工具提示也区分 `boot_load_len` 与image size。正常版本更新按文档保留fixed_inf，只改实际升级分区的有效长度。

NV文件是带U8/U16/U32/S8/S16/S32/STRING类型、字段顺序和长度的XML。文件名v1.9而内部CurrentVersion字符串为1.6；文件名不能直接当内部格式版本。必须确认二进制布局、缺省/保留字段、字符串编码和PageCRC偏移。仅知道“PageCRC清零后XOR”还不足以可靠生成256 B二进制页。

文档NV地址0x4C4000＋0x2000与工具全局NV_BACKUP_ADDR=0x56F000存在差异；后者与默认file_system范围重叠，须追踪具体产品执行路径或向厂家确认，不能选一个硬编码写入。本次没有声称已完成NV序列化或地址冲突的动态验证。

多合一文件第9页截图定义的9 B记录为type U8＋file_size int＋offset int，枚举type从2（二级boot）、3(E31)、4(COMM_NV)、5(CUSTOM_NV)、6(RFE_NV)、7(DSP0)、8(DSP1)。文件头总长80 B与这些9 B记录的组织、对齐/端序仍须核验真实样本。本目录未提供对应多合一文件；首版直接管理独立BIN，不以默认C结构sizeof代替文件格式。

## 7. 无法由当前证据宣布的能力

- 未验证ROM对无ACK、非法长度、断流的超时与重同步行为，也未验证低速Flash写入是否可跳过1.5M步骤。
- 未验证二级boot在E31/DSP损坏、分区表损坏时自动选择旧镜像的路径；文档“自动回滚”不能作为已交付功能验收。
- 工具目录中的 `mlink/log/OTA` 是空口信令解析日志，已抽查为RRC/BCCH消息，不是固件升级成功记录。
- 未从指定非标准XLSX原件解码内容。可读副本和原理图结论已交叉核对，但不把二者hash不同视为文件身份相同。
- 没有与硬件通信，所有地址/响应均是文档、配置或静态程序证据；执行前必须读回目标表并完成只读握手。

## 8. 复核方式

在本员工目录执行：

```powershell
python .\evidence\verify_inputs.py
python .\evidence\inspect_mcdt.py
```

前者仅使用Python标准库；后者依赖pefile、capstone，分析约数十秒。脚本不启动MCDT、不打开串口、不修改源EXE。`source_manifest.json`固定了当时输入；源文件改变时应先比较hash，再判断上述VA是否仍适用。

当前EXE SHA-256与员工2 V1.1相同。新增 [review_20261128.py](evidence/review_20261128.py) 直接解析PE与原始指令字节，校验版本后检查两处mode7、接收跳转表、13档波特率表、57600例外、500ms等待和5次本地配置上限；结果在 [review_20261128.json](evidence/review_20261128.json)。

VA0x14013CBAB只比较目标是否等于57600，不是“仅大于57600才发55”；0x14013CC7D传mode8；0x14013CD40设置500，0x14013CD45调用Sleep包装；0x14013CD6C尝试本地配置，失败计数至5后退出。循环每次本地尝试前都等待500ms。保留这一过程为参考profile，不把Windows工具实现延时扩大为ROM时序保证。

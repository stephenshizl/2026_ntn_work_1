# NTN固件外部Flash暂存方案

作者：员工1
日期：2026-11-28
状态：分区与实现设计，未修改FAL、未运行擦写。适用对象：经实板识别为8MiB且分区与当前OTA布局一致的产品。

## 1. 方案结论

**将外部Flash全包暂存作为具备足够NOR容量的产品升级主方案。** 按用户清单/截图缓存配套E31、DSP、二级Boot及原始NV XML，核验全部文件及NV转换产物后，再控制MS150进入ROM下载，用4KiB RAM缓存搬运。收包阶段PC中断时模组原固件仍可运行，安装阶段不再依赖PC持续供数。

当前代码以BY25Q64ES 8MiB、JEDEC 68 40 17为目标，`NTN_OTA_APP/BL2`分支的reserved范围为 `[0x212000,0x800000)`，6,217,728 B。当前LF版XML下，CA033四项原始文件合计2,716,189 B，CA034为2,722,253 B，均能放入3MiB数据区。数据大小已从本地发布包核对，Flash型号和容量仍必须在每台目标设备上探测。

4KiB RAM仍然需要，它用于PC分块落盘、缓存校验及模组写入。外部Flash解决整包保留和断线恢复问题，不替代RAM块缓存，也不增加PC RS232物理吞吐。2MiB旧板、NOR故障、容量不足或无法分配专用区域时拒绝该模式；可显式选择已经验证过的PC在线流式维护模式，不静默降级后继续承诺断线安装。

## 2. 源码布局和候选分区

依据MCU `work_v1_boot_fix @ 03b0abc3f4062178c1d5864100bdc98e9c87b905` 的 `boot/ota_layout.h` 与 `board/ports/fal_cfg.h`。以下均为 **MCU外部NOR设备偏移**，不同于MS150内部Flash偏移。

| 区域 | 起始 | 结束不含 | 处理 |
| --- | ---: | ---: | --- |
| 现有MCU OTA/工厂/配置/业务空间 | 0x000000 | 0x200000 | 保持 |
| MCU OTA scratch | 0x200000 | 0x210000 | 不得占用 |
| MCU OTA log A/B | 0x210000 | 0x212000 | 不得占用 |
| 候选ntn_stage_meta_a | 0x212000 | 0x213000 | 4KiB状态日志A |
| 候选ntn_stage_meta_b | 0x213000 | 0x214000 | 4KiB状态日志B |
| 候选ntn_stage_data | 0x214000 | 0x514000 | 3MiB整包数据 |
| 剩余reserved | 0x514000 | 0x800000 | 3,063,808 B，留待其他功能规划 |

该划分是本次设计候选，不是已经存在的FAL分区。实施时应把OTA分支的大reserved拆为以上专用区域及剩余reserved，禁止同时保留覆盖同一地址的大reserved可写别名。非OTA构建原reserved从0x200000开始，若也支持本方案，建议统一使用避让OTA后的地址，仍须核验该构建其他使用者。

规划前检查实际容量、擦除粒度、现有分区及调用者：不能只看到总容量8MiB就认为所有reserved均为空。暂存服务和主MCU OTA共用NOR时需要总线/分区互斥和供电约束，禁止并行执行两种升级。

## 3. 四组件缓存布局

采用独立文件与紧凑发布清单，不缓存RAR/tar.gz；logmap留PC。用户文字给出CA033五文件，截图实际选CA034；两套发布清单独立，不能从两版目录混选。清单记录组件ID、版本、实际长度、SHA-256、缓存偏移；MS150目标地址由已识别目标分区表和白名单确定，不能把缓存地址当目标地址。

| 组件 | MCU NOR缓存起点 | 实际长度 | 数据结束不含 | 缓存擦除结束不含 | MS150默认分区起点参考 |
| --- | ---: | ---: | ---: | ---: | ---: |
| E31 CA034 | 0x214000 | 2,509,271 B | 0x4789D7 | 0x479000 | 0x028000 |
| DSP CA034 | 0x479000 | 74,519 B | 0x48B317 | 0x48C000 | 0x3A8000 |
| 二级Boot | 0x48C000 | 122,622 B | 0x4A9EFE | 0x4AA000 | 0x008000 |
| NV原始XML（当前LF） | 0x4AA000 | 15,841 B | 0x4ADDE1 | 0x4AE000 | 不能直接烧写XML |
| 验证后的NV页预留 | 0x513000 | 专用4KiB区域 | 0x514000 | 0x514000 | 普通参考主/备区0x4C4000/0x4C6000 |

CA034四原始文件按4KiB对齐占2,727,936 B，3MiB区剩417,792 B；再预留上述4KiB NV页区后，未分配余量413,696 B。CA033相应缓存起点为E31=0x214000、DSP=0x478000、Boot=0x48B000、XML=0x4A9000，结束对齐0x4AD000，占2,723,840 B。两版逐文件hash和布局见 [review_20261128.json](evidence/review_20261128.json)。新版本必须重新计算，不写死这些长度。

完整功能目标是二级Boot＋E31＋DSP＋NV四项，验证阶段可以先做E31＋DSP，不能将其称为完整功能完成。NV XML要转换为已验证二进制，当前423 B候选尚未取得线上黄金比对；Boot需验证ROM恢复、地址及fixed_inf保持。完整包缓存不等于MS150双槽回滚。

LogMap分别约3.11/3.12MB，属于PC日志映射。CA033五个原始文件合计5,825,902 B，CA034为5,844,441 B，不能全部塞入本方案3MiB数据区。若产品要求设备保存LogMap，应另评估更大的缓存布局或更大Flash，不静默占用剩余reserved；安装E31不需要把LogMap写到模组。

## 4. 发布清单和状态记录

最小清单包括机型/硬件版本、发布ID、四组件写入选择、E31/DSP/LogMap配对关系、各文件真实长度及hash、缓存布局版本、目标分区profile、NV XML与转换二进制的对应hash/格式ID、兼容boot/NV条件及整份清单hash。PC从受信任发布清单校验来源；SHA-256不能凭空提供签名认证。

状态建议为：`EMPTY → RECEIVING → READY → INSTALLING → VERIFYING → COMPLETE`；错误保留为 `RECEIVE_ERROR` 或 `RECOVERY_REQUIRED`，分别表示模组未被改动或安装可能已开始。

两个4KiB元数据扇区采用追加记录，保存magic、schema、递增代次、状态、清单hash、组件长度/偏移/hash、记录CRC32及最后提交字。记录和提交字分次写入，先写内容并读回，再写提交字并读回。读启动记录时扫描CRC及提交字有效的最高代次；轮转前保证另一扇区有完整有效记录，再擦旧扇区。

重要顺序：

1. 接受新包前，先持久提交新代次RECEIVING，确认成功后才擦缓存数据区，避免旧READY仍指向被覆盖的数据。
2. 接收每块时校验会话、偏移、长度、CRC32；擦写缓存并读回后才向PC报告 `STORED`。ACK丢失则查询块状态或读回比对，不盲目重复擦除。
3. 全包到齐后，MCU从NOR重新读取四项原始文件及本次要求的NV二进制产物，校验固定清单hash和长度。完整profile的NV产物未验证时保持不可安装，不因原始XML已到齐而标完整READY。
4. 真正进入安装前提交INSTALLING并确认可读，随后才执行MS150首次擦除。持久标志需在普通NTN上电/AT业务之前被检查。
5. 状态记录不必对632个4KiB目标块逐块擦写元数据。首版可记录阶段，复位后由完整缓存与目标读回判定重刷；优化进度日志时另评估磨损和掉电一致性。

记录损坏、清单未知、缓存hash不符或发现新代次RECEIVING时，不能回退选取旧READY并直接安装。每次准备安装/恢复都重新核验缓存和清单；无法建立一致状态时停止并报告具体原因。

## 5. 收包与安装分离

### 收包阶段

PC通过现有RS232115200分块发送，MCU独占PC维护入口和相应NOR分区。根据资源策略暂停/限流外部业务输入，已有业务队列不清除。此时不拉模组BOOT、不擦模组Flash；PC掉线只留下未完成缓存，模组保持原版本。

启动完整安装需要清单兼容、缓存READY、供电合格、主MCU OTA空闲、NOR健康及目标身份匹配。操作者发起的安装指令与单纯接收文件结束分开，禁止下载完成即无条件重启模组。

### 安装阶段

取得UART3/电源独占后按协议进入ROM，读真实分区表、备份首4KiB及NV/设备配置，建立组件到目标分区映射。BIN从NOR读4KiB并校验，再按7A等已验证命令烧写；NV使用单独的02分页路径。四组件执行顺序以原厂完整抓包冻结，不根据UI行顺序猜测。NV转换和读回细节见 [NV专项](NV烧录文档与反汇编核查_员工1_20261128.md)。

安装开始时不再请求PC供固件字节；PC可持续接收进度，也可在设备明确支持离线安装能力后断开。首版开发验收前仍应保持PC连接以收集诊断。备份与诊断文件应保存在PC；外部缓存保留完整包，但本方案未给它额外分配整个模组旧分区备份容量。

所有选中组件均写入、读回并通过核对后，才修改MS150表中需要更新的mv_length；Boot固定头搬移长度0x2000不随文件大小改变，首扇区其余字节保留。正常启动并查询版本/配置自检通过后提交COMPLETE，释放维护所有权。

## 6. 异常与恢复

| 场景 | 行为 |
| --- | --- |
| 收包时PC断开/MCU复位 | 模组不变；检查RECEIVING，按已验证落盘块续收或重收，不安装半包 |
| 缓存读写失败或SHA不符 | 不进入模组下载/擦除，报告存储故障，不把故障NOR当可靠恢复源 |
| 安装中PC断开 | 若离线安装能力已验收，依靠已核验缓存继续；记录状态，重连后查询 |
| 安装中MCU/模组复位或断电 | MCU启动早期发现INSTALLING/RECOVERY_REQUIRED，抑制正常模组业务，重新校验缓存后重入ROM，读回判断或按扇区重刷 |
| 分区表提交中断电 | 使用备份和完整缓存重建；仍有非原子擦写窗口，不宣称自动回滚 |
| 主MCU OTA同时申请 | BUSY互斥；不覆盖scratch/log、候选镜像或模组缓存 |
| 目标硬件只有2MiB或未能识别容量 | 拒绝外部整包模式；仅在明确的流式模式条件下执行其他维护路线 |

设备自行断电后能否无人值守自动继续安装，取决于启动GPIO、有效持久记录、供电恢复、缓存校验及恢复策略的完整实现和验证。当前已有主MCU OTA不自动提供MS150安装状态机；这部分仍需开发。

## 7. 吞吐和资源

PC发送2,583,790 B在1152008N1下的纯载荷下限仍为224.287秒。外部Flash方案将这段时间移到完整收包阶段，安装阶段再计模组发送、632个块的30ms间隔、NOR读写、擦除、读回与启动；它改善阶段隔离和恢复能力，不会把总时间变成17秒。

RAM设计保持块缓存4KiB、PC帧约1KiB、读回页256B、hash上下文和线程栈等受控预算。Flash忙等待须保持task_wdt与SWDT协同，避免长时间关闭中断。最先实现读页、校验、状态查询及边界拒绝，随后才接通实际擦写。

## 8. 必须新增的验收

1. 设备报告JEDEC、SFDP容量、擦除粒度和当前FAL布局；2MiB/未知型号/容量不足被拒绝，OTA构建不能写0x200000～0x211FFF。
2. 接收CA034配套两镜像，NOR全量SHA-256一致；尾部对齐和0x514000边界检查通过，超大包/地址溢出不能擦保留区。
3. 接收阶段拔掉PC，MS150原版本仍正常；半包永不标READY；收包ACK丢失不破坏已落盘数据。
4. READY之后安装，停止PC供数仍能完整烧写；MCU通过NOR供数，没有暗中依赖PC重复请求镜像。
5. 在元数据提交、缓存擦写、目标E31/DSP擦写、表提交等阶段注入断电，验证有效记录选择、缓存复核和ROM恢复。
6. 检查主MCU OTA、Flash业务队列、参数和工厂数据未改变；串口错误、NOR故障、任务心跳超时都能退出到明确恢复态。

实施前先冻结专用分区和持久记录格式，再修改MCU代码。当前报告提交仅交付候选布局和验证依据。

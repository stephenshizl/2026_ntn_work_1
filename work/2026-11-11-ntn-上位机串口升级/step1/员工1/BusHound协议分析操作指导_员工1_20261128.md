# Bus Hound协议分析操作指导

作者：员工1
日期：2026-11-28
目标：采集MCDT对MS150的实际下载数据，核对静态协议、四组件写入、NV分页和速率切换。本文是执行指导，本次尚未采集实板数据。

## 1. 推荐起始配置

**单次完整升级先用64MiB缓冲、128KiB单阶段/记录上限、满缓冲停止。** 界面名称可能是Buffer Size/Capture Capacity、Max Phase/Max Record Length，按现场版本确认单位，记录实际设置。若菜单上限达不到，不假设输入更大数值就能解除限制。

| 项目 | 起始设置 | 理由与检查 |
| --- | --- | --- |
| 总采集缓冲 | 64MiB；短场景可用32MiB | 适合一次固件发送、读回及控制记录；保留充足余量 |
| 单阶段/记录数据长度 | 131072 B，即128KiB | 79帧为1＋4＋65536＋1＝65542 B；65536 B仍不足 |
| 满缓冲处理 | 停止采集，禁用循环覆盖 | 保住开头的握手及改速；捕获前确认行为 |
| 数据方向 | IN和OUT均开启 | 必须同时看到命令和响应 |
| 控制/配置事件 | 开启可用的CTL/Serial IOCTL等 | 记录打开COM、波特率设置及其他控制事件 |
| 时间 | 开启时间戳及相邻时间差 | 用于软件事件关联，不能替代物理波形 |
| 设备范围 | 只选目标COM或其USB-UART节点/端点 | 避免其他USB设备或日志口耗尽缓冲 |
| 停止条件 | 单次过程结束后立即停止并另存 | 不把长时运行日志和下载验证混在同一缓冲 |

若容量单位为KiB，64MiB填写65536，32MiB填写32768；若单位为字节，分别为67108864、33554432。128KiB填写131072 B。软件显示MB/KB时先看帮助或实际记录设置，不自行把单位混用。

[Perisoft官方产品页](https://perisoft.net/bushound/)列出USB和serial port支持，并明确免费版限制采集数据量。具体免费版上限及节点支持按安装版本验证，不编造固定的免费字节限制；容量不足时先按CAP分场景保存，或使用允许所需容量的版本。

## 2. 64MiB是否足够

CA034 E31＋DSP＋二级Boot有效BIN共2,706,412 B，NV双副本页写当前候选仅4×262 B命令。加上一次全镜像读回，载荷仍为数MiB；64MiB为事件元数据和适配器封装预留余量，是工程起始建议，不是“绝不丢包”的保证。LogMap JSON由PC解析，不应作为Flash镜像发送。

持续流量估算：1.5M、8N1单方向极限约150000 B/s。连续10分钟约90 MB纯载荷，尚未计软件事件和反方向。因此长时间运行或日志口并发时64MiB也可能不足；优先分段保存，观察缓冲占用与丢失/截断标志，必要时提高到128/256MiB或使用安装版本支持的流式保存方式。

Max Phase/Record约束的是软件记录，不等同于UART完整协议帧。驱动可能把一个79帧拆成多条记录，仍需按方向、命令头、长度和校验重组；也不能因为一条记录小于64KiB就认定没有截断。

## 3. 选对采集链路

### 原厂协议采集

```text
Windows MCDT → USB-UART → MS150 UART0
        Bus Hound采集COM/USB I/O
                      逻辑分析仪并联TX/RX/BOOTSEL/RESETN
```

适配器电平须符合接入侧。模组侧与经U22转换的MCU侧电平不同；需要硬件人员确认接线及驱动隔离，不能把两个TX输出并联，也不能把RS232电压接入TTL UART。优先使用已能通过原厂工具恢复的测试板。

### 产品代理链路采集

```text
PC → USB-RS232 → 终端UART1 → MCU缓存/代理 → UART3 → MS150 UART0
```

只监控PC的RS232 COM口，得到的是PC↔MCU会话，**看不到MCU内部UART3实际发送的数据和物理时序**。分析后者必须在板内UART3/模组UART0增加逻辑分析或由MCU导出受控二进制跟踪。PC口保持115200与板内安装速率1.5M是两条独立设置。

## 4. 开始采集前

1. 记录板号、硬件版本、模组当前版本、适配器型号和VID/PID、COM号、供电及接线侧。
2. 固定MCDT EXE的SHA-256和产品SharkNTN；保存选项截图。用户本次截图是CA034、勾选Boot/E31/DSP/NV及E31 LogMap，自动运行未勾选、进度0%，它说明配置而不证明升级完成。
3. 用发布清单选中同版文件。CA033的E31/DSP/LogMap来自20261010构建；CA034来自20261104构建，不能混选。记录NV XML原始hash及二进制转换版本。
4. 在MCDT打开COM之前启动Bus Hound；抓取过程不让另一个终端程序争抢串口。先做短记录，确认双向字节和控制事件确实可见。
5. 同步启动逻辑分析仪。建议从至少24MHz采样起步，视设备解码质量/电平阈值调整；软件事件精度与采样率不是信号质量验收指标，模拟边沿需要示波器查看。

ROM进入、QSPI初始化、清保护及改速都会改变设备状态；“不擦Flash”不等于完全只读。采集顺序先握手/初始化/读页，再在备份和可恢复条件齐备的样机执行擦写。

## 5. 分场景采集矩阵

| ID | 目标 | 保存什么 | 通过标准 |
| --- | --- | --- | --- |
| CAP01 | 进ROM、U、C0、46 | BOOT/RESET、完整TX/RX、初始速率 | 能关联进入下载、停止U及QSPI应答 |
| CAP02 | 两条57 | 两个10 B命令及全部RX、空闲尾部 | 关闭文本/ACK/组合、结束边界；不能只取首个06或任意2 B |
| CAP03 | 55及50改速 | 50索引、响应、COM改速控制事件及波形 | 明确ACK物理速率、本地等待及首条新速率命令 |
| CAP04 | EB读表 | 6 B命令和完整返回 | 确认256 B是否带额外ACK，重复读取一致 |
| CAP05 | E31/DSP/Boot写块 | 79/7A头、数据、XOR、末尾响应及延时 | 头长5/9 B、LEN BE32、无截断、物理头后间隔明确 |
| CAP06 | NV专项 | 擦除地址、全部02页写、主/备地址及ACK | 对照NV候选423 B/两页/末页零填充，保留任何差异 |
| CAP07 | 表提交和启动 | 首扇区前后、32、50恢复、BOOT、ATI/CGMR | 固定头和保留页正确、版本和配置自检通过 |
| CAP08 | 故障恢复 | 断线、掉电、重入和缓存状态 | 只在恢复流程已验证的板上实施，不能把重新打开COM当恢复完成 |

NV专项建议另存一次短捕获，避免被2.5MiB固件记录淹没。先分别确认四组件，再保存一次同配置的完整升级作为端到端证据。每次记录实际勾选项，不把分段试验称为完整升级。

## 6. USB封装和时序的处理

如果采到USB层数据，需区分bulk载荷、控制传输、适配器状态头和MS150字节。保留原始USB记录，再按该芯片和端点配置解封装；不能统一删除“每条记录前2 B”，因为USB包和软件记录边界不等价。

不要用USB OUT提交完成时间断言UART最后停止位时间；不要用软件IN返回时间判断ACK是在旧波特率还是新波特率发送。原工具静态代码在50应答后每次本地配置前等待500ms，可用软件控制事件辅助验证，但物理ACK速率及7A头后30ms间隔由逻辑波形确认。

重组规则：79按固定65536 B数据，7A按BE32 LEN，02按256 B数据，EB按已确认的返回格式；逐帧核对XOR初值FF。数据内部的06、55、CR、LF均可能是普通载荷，不可作为通用分隔符。

## 7. 保存和交接

建议在后续阶段建立 `step2/员工号/capture/测试ID/`，保存原生捕获、原始HEX导出、逻辑工程/解码CSV、MCDT日志、截图及manifest。原始数据先保存再分析，解封装和合帧结果另存，不能覆盖原文件。

manifest字段：测试ID、真实时间/时区、板号及版本、源/目标固件、各文件hash、工具hash及版本、设备/COM、供电/电平侧、握手/安装波特率、缓冲及记录限制、丢失/截断情况、文件hash、操作者、测试结果与未关闭项。

合帧CSV至少包括：方向、软件时间、物理时间（有则填）、速率、原始文件及偏移、操作码、地址、长度、完整HEX引用、计算CHK、线上CHK、完整RX、判定和备注。结果只能使用实际数据，不填虚构PASS。

执行前先按64MiB/128KiB做一次短捕获，核实软件没有额外容量或显示限制；完整试验后检查起始握手、末尾校验、NV全部页和最终版本记录都还存在，再接受该次捕获为有效证据。

## 1. 结论

**现有硬件连接具备升级 MS150/ST1000 模组自身固件的条件，无需为此另换一组串口。** 主 MCU 的 USART3（PB4 发送、PB5 接收）通过 U22 电平转换接到模组 UART0，而厂商指定的下载接口就是 UART0。主 MCU 还具有 BOOT、复位和模组电源控制。[S1 PDF第1、5页；S2 V30；S4 第4、6～8页；S5 第5、7页]

本板必须注意反相：**PA10=1 才是进入下载模式，PA8=1 才是复位有效**。协议所说的 BOOTSEL=0、RESET=0 是模组端电平；Q4、Q3 将 MCU 电平反相。正常运行时 PA10=0、PA8=0。BOOTSEL/RESETN 释放后的实际高电平及上电采样时序仍需实测。[S1 第1、5页；S2 V30 F30/F32；S8]

推荐实现为：**Windows 上位机经现有 RS232 → 主 MCU 外部Flash完整暂存及校验 → 升级代理/4KiB RAM搬运 → USART3 → MS150 UART0**。适用于探测为8MiB且专用区域可用的设备；在线流式路径保留为实验/旧板维护选项。当前 MCU 的 AT 透传功能不能直接作为 MCDT 烧录通道；必须新增维护模式并暂停 AT、URC 解析及自动业务发送。[S8]

2026-11-28按用户文件清单和原工具截图，将功能目标补充为 **二级Boot、E31、DSP、NV四组件完整升级**，LogMap仅用于上位机日志。先完成E31＋DSP验证，再关闭Boot和NV专项，不能以两组件成功冒称四组件完成。CA033与CA034当前boot/NV相同是内容比较结果，不能据此取消完整升级能力要求；具体会话严格按发布清单决定写入项，不整片擦除。

可进入软件开发和实板验证阶段，但在实板串口握手、1.5 M 波特率、读回、掉电恢复验证完成前，不能宣布“已可用于现场升级”。厂商资料存在可由原工具补正的协议错误，详见配套《协议核对与参考工具分析》。

### 3.1 原工具配置中的分区

下表来自 `mlink/config/sharkNTN/flashPartition.ini`，是 **工具默认配置，不是从目标模组读出的实时分区**。实际烧录以模组读回并验证后的表为准；不匹配时拒绝自动写入。

| 区域 | 起始偏移 | 配置容量 | 当前 CA034 实际长度 | 实施处理 |
| --- | ---: | ---: | ---: | --- |
| 分区表 | 0x000000 | 首页256 B，位于首个4KiB扇区 | 按实际版本 | 备份首个完整4KiB，最后提交 |
| 二级 boot | 0x008000 | 0x020000 | 0x01DEFE | 完整profile需支持刷新；独立验证，保留fixed_inf |
| E31 | 0x028000 | 0x380000 | 0x2649D7 | 升级，最终 mv_length 取真实长度 |
| DSP0 code | 0x3A8000 | 0x060000 | 0x012317 | 与 E31 同版本更新 |
| cfg_nv | 0x4C4000 | 0x003000 | XML需转换；423 B为当前静态候选 | 完整profile需支持，先备份并确认主/备页 |
| file_system | 0x4D0000 | 0x300000 | 未读取目标 | 不擦除 |

工具配置 `S_MV_LENGTH=0x2000` 与 boot 文件长度 0x1DEFE 不同。前者是 ROM/boot 启动搬移长度，不能改成整个文件大小；EXE 内也有 `bytes to copy for 2nd-boot (not image size)` 提示。保留目标 fixed_inf，而不是重新按文件大小构造固定头。[S4 第5～6页；S7；S9]

NV文档第7～8页3.3节有专门烧录指导。本次进一步追踪原工具：普通NV对象从cfg_nv_part读起点/容量，擦整个配置区，分页写主区后以＋0x2000写备份；特殊标志有另一条扇区位移路径，不能把全局NV_BACKUP_ADDR直接套入。423 B、CRC42、两页及尾页填零是当前静态候选，还须与原工具实际02帧逐字节比对。详见 [NV专项核查](NV烧录文档与反汇编核查_员工1_20261128.md)。

CA034 按4KiB扇区处理：E31擦除 `[0x28000,0x28D000)`，613个扇区；DSP擦除 `[0x3A8000,0x3BB000)`，19个扇区。均落在上述默认分区内。这只证明本地镜像与配置的静态边界成立，不证明实板分区一致。

## 4. 必须处理的协议问题

| 项目 | 核查结果 | 方案要求 |
| --- | --- | --- |
| `EB 00 00 00 00 14` | `14 = FF XOR EB`，原工具按256 B接收并复制整页；文档解释成读取20 B是错误 | 固定页读命令，不把14当长度 |
| `50 09` | 文档部分步骤省略校验，实际帧应为 `50 09 A6` | 区分命令本体与完整帧，避免漏加/重复加校验 |
| `7A` LEN | 原工具生成4字节大端长度，9字节头 | 不能使用1/2字节长度或小端长度 |
| `57` 回复 | 两次调用均传mode7，累计至少2 B；并非单字节06判定 | 必须抓完整回复及结束边界，不能把任意2 B视为成功 |
| `50` 改速 | mode8检查首字节06；每次本地改速尝试前等待500ms，最多5次本地配置 | 不是重发50五次；ACK在线速率仍需实测 |
| Flash表内整数 | 原工具的读取助手按小端解释，直接复制页的路径与x64小端布局一致 | 命令地址/长度大端；Flash结构整数小端，分别编码 |
| 写入节拍 | 文档规定头和数据间30ms，反汇编也见30,000,000ns等待 | MCU缓存完整待写块后发头、等待≥30ms、连续发数据及校验 |
| NV | XML需要按类型/长度转二进制页、PageCRC清零重算，再写主/备份 | 不把XML文本作为镜像；未验证前禁止写 |
| 回滚 | 远程方案宣称自动回滚，但下载协议与当前默认表没有交付可验证的旧镜像双槽切换流程 | 首版按原地更新设计，失败走ROM重新烧录，不承诺自动回滚 |

反汇编只用于补充该版本 MCDT 的主机端实现。尚未逆向或验证模组 ROM/二级 boot 的全部行为，不能以 EXE 中存在某条分支证明目标固件一定支持它。详细地址和证据见 [协议核对与参考工具分析](协议核对与参考工具分析_员工1.md)。

## 5. 现有软件差距

2026-11-28重新核对 RT-Thread `work_v1_boot_fix @ 03b0abc3f4062178c1d5864100bdc98e9c87b905` 中的 `bsp/hc32/ev_hc32f460_lqfp100_v2` 及公共串口驱动，只读源码。本地、局域网关键源码归一化换行后相同，GitHub该分支指向同一提交；本地另有既存构建产物/IDE配置改动，不属于此次报告提交。

1. `board/board_config.h:71～76` 已定义 PB15、PA8、PA10 等控制脚；`ntn_ms150.c:893` 使用 UART3 PB4/PB5、115200 8N1。
2. `ntn_rx_thread_entry()` 会把每个接收块同时送入 AT事务、URC行处理和现有回调。下载模式需要在这些解析之前切换到二进制专用接收路径，保持唯一 UART 读者，不能再创建抢读线程。
3. 现有 PC→NTN 路径按 AT 行装配/本地命令识别，不能保证任意 `00/0D/0A`、0x06及镜像字节原样通过。
4. `hw_power_ntn_set(true)` 在“已经上电”与“新上电”路径均将 BOOT 拉低。直接复用此函数进入升级会清除 PA10 下载模式。需要专用且受会话控制的 `enter_download`，或给电源控制显式传入启动模式。
5. `.config:425～426` 未启用 UART3 RX/TX DMA。不能把现有115200 AT收发当成1.5M可靠性证明。升级前验证驱动改速、实际误差和接收过载；需要时再配置DMA或优化ISR。
6. `AT+MCUUPG?` 已按构建区分：`NTN_OTA_APP` 下为 `supported:true`、`PC_FULL`、`ymodem-1k`；非OTA构建仍为false。它描述主MCU升级，不能作为MS150升级能力。模组升级另设能力项，并与MCU OTA互斥。[S8/S10]
7. `bsp/hc32/libraries/hc32_drivers/drv_usart.c:386` 的轮询putc只等待TX_EMPTY后写数据，函数返回不保证最后停止位已发完。30ms头数据间隔和切速前需使用TX_CPLT确认硬件发送完成；RX错误处理清标志/读数据，维护模式需能发现溢出、帧错、校验错并中止当前块。
8. 时钟来自内部HRC/MPLL，且有回落HRC路径；不能用目标100MHz分频估算替代当前实际时钟和波形测量。已有task_wdt与OTA BL1 SWDT，暂停业务时必须协调其监控和心跳，不以单独喂一个硬件狗代替所有任务状态。

图中 MCU 外置 NOR U11 标注 `ZD25WQ16CEIGR`；现行 `app_flash.c` 按 `BY25Q64ES 8MiB / JEDEC 68 40 17` 探测，这是源码目标，不代表本轮读过样机JEDEC。`fal_cfg.h` 有两套构建布局：非OTA分支download=512KiB、reserved从0x200000开始；OTA APP/BL2分支由 `boot/ota_layout.h` 定义download=0x5E000、scratch位于 `[0x200000,0x210000)`、两个日志扇区位于 `[0x210000,0x212000)`，reserved从 **0x212000** 开始，至0x800000，容量6,217,728 B（5.9296875MiB）。不能沿用旧报告从0x200000开始暂存的建议。

两种download分区均放不下完整模组包。按用户要求改为外部Flash整包暂存主方案：候选元数据A/B位于0x212000/0x213000，3MiB数据区为 `[0x214000,0x514000)`，容纳E31、DSP、Boot和原始NV XML；LogMap留PC，另预留验证后的NV页存储。CA034四原始文件按4KiB对齐占2,727,936 B，能放下。该区域必须经容量探测、现有使用者核查和FAL专用分区落地后才能启用。详见 [外部Flash方案](NTN固件外部Flash暂存方案_员工1_V1.0_20261128.md)。

## 6. 推荐工作流程

```text
上位机校验机型、发布清单、E31/DSP长度和hash
  → MCU先将四组件资料完整落盘到专用外部Flash并读回校验，提交READY
  → NV XML按已验证规范转二进制，完整profile要求Boot/NV验证通过
  → 查询当前ATI/CGMR、确认现场boot/NV兼容性
  → MCU进入维护会话：独占串口/电源、暂停业务、禁止休眠
  → PA8=1保持复位，PA10=1选下载，保证电源稳定
  → 清空接收残留，UART3设115200 8N1，PA8=0释放复位
  → 等待连续U，再发C0 3F停止U并建立协议
  → 初始化Flash、解除写保护、配时钟；按验证过的profile切到1.5M
  → 读分区表和首4KiB、备份NV/设备专属区并核验白名单
  → MCU从外部Flash逐块取数，按会话profile更新Boot/E31/DSP/NV并读回校验
  → 全部镜像验证完成，保留原字段修改mv_length，最后更新分区表
  → 恢复115200，PA10=0，复位启动
  → ATI/CGMR版本匹配＋基本功能自检通过，再恢复业务并报告成功
```

复位脉宽、上电稳定时间、连续U数量、ACK等待时间属于待实板标定参数，不把经验值写成厂商时序保证。首次试验可沿用当前200ms复位脉宽，抓波形确认后固化。

每一块必须先完整缓存并校验，再开始模组下载命令。MCU对PC的“已收数据”和“模组已写入并读回一致”分开回复；进度按后者递增。任意失败停止后续擦写，保存分区表及会话记录。具体会话协议、恢复策略和验收用例见 [实施方案](NTN串口升级实施方案_员工1.md)。

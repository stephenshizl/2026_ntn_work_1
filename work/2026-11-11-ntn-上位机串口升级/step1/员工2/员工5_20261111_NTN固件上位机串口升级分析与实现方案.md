## 1. 执行摘要

### 1.1 最终结论

**可以实现通过产品外部 RS232 串口，由 Windows 上位机升级 NTN 模组固件；不需要增加新的主 MCU UART 硬件接口。**

但必须准确理解硬件链路：

```text
Windows 上位机
    │
    │ RS232（建议 115200，8N1）
    ▼
产品 RS232 接口 / J1
    │
    ▼
SP3232E（RS232 电平转换）
    │
    ▼
HC32F460 主 MCU UART1
    │
    │ MCU 升级代理：控制 GPIO、切换 NTN 侧波特率、收发二进制数据
    ▼
HC32F460 主 MCU UART3
    │
    ▼
TXB0104（电平转换）
    │
    ▼
MS150 / ST1000 UART0
    │
    ▼
NTN Bootloader / Flash 下载协议
```

主 MCU 还可以控制：

- `MCU_NTN_BOOT`：通过 Q4 控制模组 `BOOTSEL`，模组侧 BOOTSEL 低有效。
- `MCU_NTN_RST`：通过 Q3 控制模组 `RESETN`。
- `MCU_NTN_PWR_EN`：通过 Q7102 和 PMOS Q1 控制 `VCC_ST1000` 电源。

因此，**硬件具备“PC—MCU—NTN”的完整升级通道和进入 Bootloader 的控制条件**。

### 1.2 不能直接照搬 MCDT 的原因

厂家《MS150 固件下载流程》规定：模组 UART0 在下载准备阶段为 115200，随后执行 `50 09` 切换至 1.5 Mbps。

但产品外部 RS232 接口经过 `SP3232E`。MaxLinear 官方产品资料给出的 SP3232E 最大数据速率为 120 kbps；这条 RS232 链路不能承担 1.5 Mbps。相反，模组侧 `TXB0104` 的标称最大数据速率为 100 Mbps，1.5 Mbps 不构成其标称速率瓶颈。

因此：

- PC ↔ MCU：保持 115200，8N1。
- MCU UART3 ↔ NTN UART0：先 115200，收到切换成功应答后改为 1.5 Mbps。
- **不能让 Windows 上位机在 `50 09` 后把外部 RS232 COM 口切换到 1.5 Mbps。**
- 不能把 MCU 简单做成“两个 UART 原样改波特率的透明转发器”；应提供带控制命令、数据分帧、缓存和状态反馈的升级代理。

### 1.3 推荐方案

采用“**Windows 上位机升级协议引擎 + HC32F460 MCU 升级代理 + MS150 原生 UART0 下载协议**”的分层方案：

1. Windows 上位机负责读取升级包、校验文件、解析固件组件、执行 MS150 下载协议、显示进度和保存日志。
2. HC32F460 负责控制 BOOTSEL/RESET/电源、管理 UART3 波特率、把上位机二进制数据可靠转发到 NTN UART0，并把模组应答回传。
3. MCU 正常运行时保持原有 RS232/NTN AT 透传；进入升级模式后独占 UART1/UART3，暂停普通 AT 透传，升级结束后恢复。

## 3. 原理图硬件链路分析

### 3.1 外部 PC RS232 → 主 MCU UART1

原理图依据：

- 第 2 页：J1 接口引出 `RS232_RX`、`RS232_TX`。
- 第 3 页：U4 为 `SP3232E`，完成 RS232 电平与 MCU UART 逻辑电平转换。
- 第 5 页：主 MCU U6 的 `PA0/ADC1_IN0`、`PA1/ADC1_IN1` 分别连接 `MCU_UART1_RX`、`MCU_UART1_TX`。

链路如下：

| 方向 | 信号链路 | MCU 管脚 |
|---|---|---|
| PC → MCU | J1 `RS232_RX` → U4 SP3232E → `MCU_UART1_RX` | U6 PA0，Pin 10 |
| MCU → PC | `MCU_UART1_TX` → U4 SP3232E → J1 `RS232_TX` | U6 PA1，Pin 11 |

结论：

- 外部 PC 串口不是直接接到 NTN 模组。
- 外部 PC 串口首先接入主 MCU UART1。
- 这条链路可以继续承担产品正常 AT 透传，也可以在 MCU 增加升级模式后承担升级控制和固件数据传输。

### 3.2 主 MCU UART3 → NTN UART0

原理图依据：

- 第 1 页：U7（ST1000）UART0 信号：
  - Pin 33：`UART0_TXD`，网名 `NTN_UART0_TXD`。
  - Pin 32：`UART0_RXD`，网名 `NTN_UART0_RXD`。
- 第 1 页：U22 为 `TXB0104RUTR`，A 侧连接模组 `VDDIO_AON` 域，B 侧连接 `VCC_MCU_3V3` 域。
- 第 5 页：`MCU_UART3_RXD`、`MCU_UART3_TXD` 通过 R3/R4（0 Ω）接到 MCU。

信号方向：

| 数据方向 | 模组侧 | 电平转换 | MCU 侧 |
|---|---|---|---|
| MCU → NTN | `NTN_UART0_RXD`（U7 Pin 32） | U22 IOA3 ↔ IOB3 | `MCU_UART3_TXD`，U6 PB4，Pin 40 |
| NTN → MCU | `NTN_UART0_TXD`（U7 Pin 33） | U22 IOA4 ↔ IOB4 | `MCU_UART3_RXD`，U6 PB5，Pin 41 |

注意：这里的 UART3 是 **HC32F460 主 MCU 的 UART3**；它连接的是 **NTN 模组的 UART0**。不能把两个芯片的 UART 编号混为一谈。

U22 的供电关系：

- VCCA：`VDDIO_AON`。
- VCCB：`VCC_MCU_3V3`。
- OE：连接到 `VDDIO_AON`。
- 这是一条专用的逻辑电平转换通道，不是 RS232 电平通道。

TI 官方资料标注 TXB0104 最大数据速率为 100 Mbps，标称速率远高于 1.5 Mbps。最终仍需结合实际 VDDIO 电压、PCB 走线、负载和波形进行实测。

### 3.3 BOOTSEL、RESET、PWR_EN 控制链路

原理图第 1 页和第 5 页：

| MCU 信号 | MCU 管脚 | 外围电路 | 模组信号 | 逻辑判断 |
|---|---|---|---|---|
| `MCU_NTN_BOOT` | U6 PA10/USB_ID，Pin 31 | Q4：DTC123JET1G，NPN 下拉 | `BOOTSEL` | MCU 输出高 → Q4 导通 → BOOTSEL 被拉低 |
| `MCU_NTN_RST` | U6 PA8，Pin 29 | Q3：DTC123JET1G，NPN 下拉 | `RESET_ST1000` / RESETN | MCU 输出高 → Q3 导通 → RESETN 被拉低 |
| `MCU_NTN_PWR_EN` | U6 PB15，Pin 28 | Q7102 控制 PMOS Q1 | `VCC_ST1000` | MCU 输出高 → Q7102 导通 → PMOS 打开，模组上电 |

关键说明：

1. 厂家《MS150 远程升级方案》明确 BOOTSEL 为低有效。
2. 原理图中的 Q4/Q3 是 NPN 下拉控制，所以 MCU 软件侧的控制逻辑与模组侧电平相反：
   - `MCU_NTN_BOOT = 1`：把模组 BOOTSEL 拉低。
   - `MCU_NTN_RST = 1`：把模组 RESETN 拉低。
3. `MCU_NTN_PWR_EN = 1` 从原理图电路关系看用于打开模组电源；仍应在实板上用万用表/示波器确认上电、掉电时序。
4. BOOTSEL 的非有效状态在原理图中没有看到明确外部上拉电阻，需核对模组内部上拉或实板电平，不能仅凭 MCU GPIO 输出低就认定 BOOTSEL 一定为高。

### 3.4 硬件可行性结论表

| 项目 | 判断 | 说明 |
|---|---|---|
| PC 与 MCU 通信 | 可行 | 已有 RS232 → SP3232E → UART1 |
| MCU 与 NTN UART0 通信 | 可行 | 已有 UART3 → TXB0104 → UART0 |
| MCU 控制进入 Bootloader | 硬件具备条件 | 已有 BOOTSEL、RESET、PWR_EN 控制链 |
| 模组侧 1.5 Mbps | 原理图具备基础 | TXB0104 标称速率足够；需实测 UART3 配置和信号质量 |
| PC 侧直接 1.5 Mbps | 不可行/不应采用 | SP3232E 最大速率 120 kbps；且 MCU 位于 PC 与模组之间 |
| 无新增硬件实现 | 可行 | 使用现有 UART1、UART3、BOOT、RESET、PWR_EN |
| 现有 MCU 固件已经支持升级 | 未知 | 没有本次 MCU 工程源码和运行日志，不能确认 |

## 4. 厂家升级协议分析

### 4.1 协议定位

《MS150 固件下载流程》说明：上位机或 AP 主机通过 UART0 发送特定二进制命令，完成 QSPI Flash 初始化、解除写保护、擦除、写入、NV 更新、分区表更新和启动。

该文档明确适用于：

- 开发阶段固件调试；
- 量产工具编写；
- FOTA 方案中 AP 主机对 MS150 的本地 UART 烧录。

本项目采用的是其中“AP 主机通过 UART0 本地烧录”的方式；PC 上位机通过主 MCU 代理实现 UART0 访问，不使用 NTN 卫星链路下载固件。

### 4.2 进入 Bootloader

厂家资料给出的关键条件：

- BOOTSEL：低有效。
- 复位：AP 控制 RESET。
- 模组进入烧录模式后，UART0 以 115200 波特率持续输出字符 `U`。
- AP 检测到连续 `U`，确认进入升级模式。

《MS150 操作指导手册》第 6 页给出的开发板操作是：

1. `UART_BOOT` 拨到 ON。
2. 重新将 `PWR_EN` 拨至上电状态。
3. 观察开始输出 `U`。
4. 上位机点击下载。

《MS150 远程升级方案》第 7 页描述的是 BOOTSEL 拉低后，通过 RESET 或控制电源复位模组。

结合本产品原理图，建议优先采用可控的上电采样方式：

1. MCU 暂停正常 NTN AT 透传，独占 UART1/UART3。
2. `MCU_NTN_BOOT = 1`，使 BOOTSEL 被拉低。
3. `MCU_NTN_PWR_EN = 0`，关闭模组电源。
4. 等待模组电源充分掉电（具体时间需厂家确认）。
5. `MCU_NTN_PWR_EN = 1`，重新给模组上电。
6. 保持 BOOTSEL 有效，UART3 配置为 115200。
7. 等待 UART3 收到连续 `U`，进入下一步。
8. 若未收到 `U`，记录超时和串口数据，按厂家确认的时序重试；不要无限循环上电。

该顺序与开发板手册的“UART_BOOT ON 后重新 PWR_EN 上电”一致。最终应由厂家确认上电采样时序、掉电时间和是否允许仅使用 RESET 进入下载模式。

### 4.3 Flash 下载准备命令

按厂家《MS150 固件下载流程》第 6～7 页：

| 顺序 | 指令（十六进制） | 用途 | 成功条件 |
|---:|---|---|---|
| 1 | `C0 3F` | 读取版本，使芯片停止输出 U 码；文档要求忽略返回值 | 按文档继续 |
| 2 | `46 B9` | 初始化 QSPI Flash | 返回 `0x06` |
| 3 | `57 56 80 00 18 06 00 00 01` | 清除写保护（1） | 返回内容包含文档指定的成功字段 |
| 4 | `57 56 80 00 24 00 00 02 00` | 清除写保护（2） | 返回内容包含文档指定的成功字段 |
| 5 | `55 AA` | 配置时钟 | 返回 `0x06` |
| 6 | `50 09` | 切换 UART0 波特率到 1.5 Mbps | 返回 `0x06`；模组侧 UART 必须同步切换 |

校验码 CHK：

```c
uint8_t chk = 0xFF;
for (size_t i = 0; i < command_len; ++i) {
    chk ^= command[i];
}
```

文档示例：

- `C0` → CHK `3F`
- `46` → CHK `B9`
- `50 09` → CHK `A6`

注意：这是 MS150 协议的 8 bit XOR 校验，不等同于本项目建议的 PC↔MCU 升级代理帧 CRC。

### 4.4 Flash 擦除和写入

厂家文档定义：

| 命令 | 功能 | 地址/长度约束 |
|---|---|---|
| `0x20 [SADDR] [CHK]` | 擦除一个 4 KB Sector | SADDR 按 4 KB 对齐 |
| `0xD8 [BADDR] [CHK]` | 连续擦除一个 64 KB Block | BADDR 按 64 KB 对齐 |
| `0x79 [PADDR] [DATA_64K] [CHK]` | 写入连续 64 KB 数据 | PADDR 按 256 B 对齐 |
| `0x7A [PADDR] [LEN] [DATA_VAR] [CHK]` | 写入不超过 64 KB 的变长数据 | PADDR 按 256 B 对齐 |

其他要求：

1. 写入前必须先擦除对应 Sector/Block。
2. 擦除范围较大时优先使用 `0xD8`，减少擦除命令次数。
3. 数据不满 64 KB 时，优先使用 `0x7A`，避免不必要覆盖。
4. 命令头与数据之间需要 30 ms 延时。
5. `SADDR`、`PADDR`、`BADDR`、`LEN` 按大端序。
6. 文档没有完整明确 `0x7A` 的 LEN 字段宽度、命令应答格式、超时时间和重试边界；编码前必须向厂家确认。

### 4.5 NV 下载

厂家文档第 7 页给出的 NV 操作：

1. 解析 XML 格式 NV 文件。
2. `PageCRC` 字段先清零，再重新计算；算法为 XOR，初值 `0xFF`。
3. 从 Flash 分区表获取 `cfg_nv` 地址；文档示例为 `0x4C4000`。
4. 擦除 NV 分区，使用 4 KB Sector Erase（`0x20`）。
5. 使用 `0x02` 命令按 256 字节写入主区。
6. 备份区地址：`0x4C4000 + 0x2000 = 0x4C6000`。

风险与实现要求：

- NV XML 不能当作普通 BIN 原样写入。
- XML 解析、字段类型转换、PageCRC 计算建议在 Windows 上位机完成。
- 不应默认每次升级都覆盖 NV；NV 可能包含产品配置、射频/网络参数和运行配置。
- 升级前应明确是否需要更新 NV、是否先备份旧 NV、主区/备份区的生效关系。
- 本次固件包文件名为 `shark_ntn_config_nv_v1.9.xml`，但 XML 内部 `CurrentVersion` 为 `1.6`；不能把文件名版本直接当成 XML 数据版本，需厂家确认兼容关系。

### 4.6 分区表

厂家文档第 5～6、8 页定义了分区表结构：

```c
struct partition_t {
    unsigned int offset;
    unsigned int size;
    unsigned int mv_length;
};
```

`T_Header_5gNew` 包含：

- 固定头 `fixed_inf`；
- `rfe_nv`、`revd_part`；
- `firmware`（E31）；
- `dsp0_code`；
- 其他 DSP、FOTA、异常、NV、文件系统分区；
- `stamp` 和保留字段。

文档特别强调：

1. `fixed_inf` 不得修改，ROM 与 second boot 依赖此结构。
2. `firmware`、`dsp0_code` 等分区字段的位置不能随意调整。
3. 一般仅修改实际烧录分区的 `mv_length`。
4. 如果确实修改分区配置，必须同步更新 offset、size，并保证二级 Boot 和 E31 读取逻辑一致。
5. 分区表写入前先擦除偏移 0 所在 Sector，再用 `0x32` 将 256 字节分区表写回。

文档给出的命令：

```text
读取：EB 00 00 00 00 14
擦除：20 00 00 00 00 DF
写入：32 00 00 00 00 [DATA_256] [CHK]
```

**重要协议疑点：**

- 文档将 `EB 00 00 00 00 14` 解释为从地址 0 读取 `0x14`（20）字节。
- 但同一文档定义的 `T_Header_5gNew` 字段总长度按结构计算为 256 字节；MCDT 静态字符串也出现“256 bytes, 1 page(s)”。
- 仅读取 20 字节不能得到完整 256 字节分区表，也就无法按文档描述读取 `firmware`、`dsp0_code` 等后续字段。

**在厂家澄清前，不得自行把 `0x14` 改成 `0x100`，也不得假设读取长度字段是页数或字数。** 需要通过厂家协议确认或对 MCDT 实际通信抓包来确定完整读表命令。

### 4.7 恢复波特率和启动

厂家文档第 8 页：

```text
50 04 AB
```

- 将 UART0 恢复到 115200。
- 收到成功返回 `0x06` 后，AP 必须立即将模组侧 UART 波特率恢复为 115200。

启动方式二选一：

```text
软件启动：B0 4F
硬件启动：BOOTSEL 切换为高电平，然后对芯片硬件复位
```

结合本产品电路，升级完成后建议：

1. 模组侧 UART3 恢复为 115200。
2. `MCU_NTN_BOOT = 0`，释放 BOOTSEL 下拉。
3. 使用 RESET 或 PWR_EN 按厂家时序重启模组。
4. 等待 `RDY`/启动完成。
5. 通过 `ATI` 或 `AT+CGMR` 查询版本。
6. 与升级包预期版本比较。
7. 恢复 MCU 正常 AT 透传模式。

### 7.2 为什么不建议 MCU 缓存整个升级包

本次固件包中的 E31 BIN 约 2.5 MB，整个升级包也超过 2.7 MB。主 MCU 不应依赖 RAM 缓存完整固件，也不应把固件包整体复制到 MCU 内部 Flash。

推荐：

- Windows 上位机保存和解析完整固件包。
- MCU 只维护有限大小的环形缓冲区/分块缓存。
- PC 按序发送数据块，MCU 收到后转发给模组 UART0。
- 每个传输块带序号、长度和 CRC；MCU 返回接收/转发状态。
- 模组原生下载协议的 CHK 由 PC 协议引擎计算，或由 MCU 进行增量计算；必须保证模组最终收到的字节流完全符合厂家协议。

### 7.3 PC↔MCU 升级代理协议（建议定义，不是厂家协议）

建议新增独立的二进制控制帧，避免将升级控制命令混入 NTN 原生 AT 透传数据。

建议帧格式：

```text
+--------+--------+---------+---------+---------+---------+----------+
| SYNC1  | SYNC2  | VERSION | CMD     | SEQ     | LEN     | PAYLOAD |
| 0xA5   | 0x5A   | 1 Byte  | 1 Byte  | 2 Bytes | 2 Bytes | N Bytes |
+--------+--------+---------+---------+---------+---------+----------+
| CRC16 (2 Bytes)                                                   |
+-------------------------------------------------------------------+
```

建议使用 CRC16-CCITT-FALSE 作为 PC↔MCU 帧校验；这只是本项目的代理协议建议，不能替代 MS150 原生 CHK。

建议 CMD：

| CMD | 名称 | 作用 |
|---:|---|---|
| `0x01` | GET_INFO | 查询 MCU 升级代理版本、能力、当前状态 |
| `0x02` | ENTER_BOOT | MCU 设置 BOOTSEL 并控制模组上电/复位 |
| `0x03` | SET_NTN_BAUD | 设置 MCU UART3 的模组侧波特率 |
| `0x04` | TX_NTN_DATA | 将 PAYLOAD 原样发送到 NTN UART0 |
| `0x05` | RX_NTN_DATA | 将模组返回数据上报给 PC；也可设计为异步数据帧 |
| `0x06` | RESET_NTN | 控制模组复位 |
| `0x07` | POWER_CYCLE_NTN | 控制模组电源掉电/重新上电 |
| `0x08` | EXIT_BOOT | 释放 BOOTSEL，退出升级模式 |
| `0x09` | ABORT | 请求安全中止当前升级流程 |
| `0x0A` | GET_STATUS | 查询当前升级状态和最近错误码 |

协议要求：

1. PC 侧 COM 口固定 115200、8N1，不随 MS150 的 1.5 Mbps 切换。
2. MCU 收到 `SET_NTN_BAUD=1500000` 后，只修改 UART3。
3. MCU 不能把 PC↔MCU 的帧头、CRC、序号等内容转发给 NTN；只转发 `TX_NTN_DATA` 中的 PAYLOAD。
4. 模组返回字节通过 `RX_NTN_DATA` 回传，必须保持二进制透明，不能按 `\\r\\n` 分行。
5. `TX_NTN_DATA` 建议每帧 512～2048 字节；具体最大长度按 MCU 缓冲和 PC 串口稳定性实测确定。
6. MCU 应返回序号、长度、CRC/状态，避免 PC 不知道某一段是否已经送达。
7. 升级期间禁止普通 AT 透传和其他线程同时访问 UART3。

### 7.4 MCU 端 RT-Thread 实现建议

建议模块划分（实际目录应以当前工程为准）：

```text
ntn_upgrade/
├── ntn_upgrade_proxy.c       // 升级状态机、会话管理
├── ntn_upgrade_proxy.h
├── ntn_upgrade_frame.c       // PC↔MCU 帧解析、CRC、序号
├── ntn_upgrade_frame.h
├── ntn_upgrade_uart.c        // UART1/UART3 收发与波特率切换
├── ntn_upgrade_uart.h
├── ntn_upgrade_gpio.c        // BOOTSEL/RESET/PWR_EN 控制
└── ntn_upgrade_log.c         // 过程日志与错误码
```

实现要点：

- UART1 由 PC 升级代理接管时，停止普通 AT 透传接收线程向 NTN 转发。
- UART3 只允许升级任务访问，禁止 AT 线程、调试线程同时写入。
- 串口 ISR 只做数据搬运、环形缓冲和信号通知，不做 Flash 协议解析或延时。
- 优先使用 DMA + 环形缓冲；若当前 UART 驱动不支持 DMA，应评估 1.5 Mbps 下中断负载和丢字节风险。
- 波特率切换必须在收到模组 `0x06` 后执行，并清理/确认 UART 接收 FIFO 状态，避免旧速率残留字节被新速率解析。
- 30 ms 命令头/数据间隔由 PC 协议引擎或 MCU 状态机严格控制，不要在中断里 `sleep`。
- 增加升级互斥锁、看门狗喂狗、总超时、分阶段错误码。
- 发生异常时，不能直接恢复普通 AT 透传；应先按安全退出流程恢复模组波特率、BOOTSEL、复位和状态。

任何阶段失败进入 `ERROR_RECOVERY`：

1. 记录阶段、最后命令、应答、波特率、分区地址、文件和数据块序号。
2. 尝试按已知状态恢复 UART3 到 115200。
3. 释放 BOOTSEL，按厂家确认的安全流程重启。
4. 不确定 Flash 是否写入完整时，不得直接宣告升级成功。

### 10.2 本产品 MCU 侧必须确认

1. 当前 UART1 是否已经用于 RS232 AT 透传，能否安全切换为升级代理。
2. 当前 UART3 是否已经初始化为 NTN UART0 通信口，是否存在其他线程访问。
3. PB4/PB5 是否在当前 GPIO/PinMux 表中配置为 UART3，是否与其他外设冲突。
4. PA10、PA8、PB15 是否已经配置为 BOOT、RESET、PWR_EN GPIO，默认输出状态是否安全。
5. 当前 RT-Thread UART 驱动在 1.5 Mbps 下是否支持 DMA/中断稳定收发。
6. MCU 是否有足够的 RAM 作为双向环形缓冲；不要求缓存完整固件包。
7. 升级期间看门狗、低功耗、异常复位和模组掉电管理如何处理。

## 11. 测试与验收计划

### 阶段 A：硬件电气验证

| 用例 | 操作 | 通过标准 |
|---|---|---|
| A01 | PC 通过 J1 RS232 与 MCU UART1 通信 | 115200、8N1 稳定收发，无乱码 |
| A02 | MCU 控制 `MCU_NTN_BOOT` | 能测得 BOOTSEL 被拉低；释放后回到非有效状态 |
| A03 | MCU 控制 `MCU_NTN_RST` | RESETN 拉低/释放时序符合厂家要求 |
| A04 | MCU 控制 `MCU_NTN_PWR_EN` | VCC_ST1000 能按预期断电/上电 |
| A05 | UART3 与 UART0 通信 | 115200 和 1.5 Mbps 均可稳定收发 |
| A06 | TXB0104 波形测试 | 无明显过冲、振铃、边沿异常和丢字节 |

### 阶段 B：Bootloader 与协议验证

1. 正常启动时，确认模组处于正常 AT 状态。
2. MCU 拉低 BOOTSEL 并按厂家时序复位/上电。
3. UART3 115200 收到连续 `U`。
4. 执行 `C0 3F`、`46 B9`，确认应答。
5. 执行两条清写保护命令，逐字节记录应答。
6. 执行 `55 AA`、`50 09`，确认 UART3 切换到 1.5 Mbps 后仍可正常收发。
7. 执行 `50 04 AB`，确认 UART3 可恢复到 115200。

### 阶段 C：固件组件验证

建议在可恢复的测试模组/开发板上按顺序进行：

1. 先验证分区表读取与解析，不写 Flash。
2. 验证擦除命令地址和边界，不对生产设备做全片擦除。
3. 按厂家确认的最小风险组件方案先升级 E31。
4. 验证 ATI / AT+CGMR 版本。
5. 再验证 DSP0 与 E31 的成套升级。
6. 最后单独验证 NV 主区/备份区写入。
7. Second Boot 更新必须在厂家明确地址、长度和恢复方法后进行。

### 阶段 D：异常与可靠性测试

| 用例 | 故障注入 | 预期结果 |
|---|---|---|
| D01 | 固件包 SHA256 错误 | 不允许进入 Bootloader |
| D02 | PC 串口断开 | MCU 记录错误并按安全流程退出或保持可恢复状态 |
| D03 | 某命令应答超时 | 定位到具体命令，不盲目继续写入 |
| D04 | 数据块 CRC 错误 | 拒绝该块或按协议重新传输 |
| D05 | 升级过程中模组复位 | 不宣告成功，进入恢复流程 |
| D06 | 升级过程中整机断电 | 验证能否通过 Bootloader 恢复；确认是否存在回滚 |
| D07 | 升级后重新上电 | ATI/AT+CGMR 与目标版本一致 |
| D08 | 升级完成后正常 AT 透传 | RS232 与 NTN 正常通信，升级模式已完全退出 |

### 阶段 E：验收条件

- PC 端只需要连接产品 RS232，不需要拆机接触模组 UART0。
- PC 端串口固定 115200，升级过程不要求 PC COM 切换到 1.5 Mbps。
- MCU 能控制模组进入/退出 Bootloader。
- E31、DSP0、NV 等组件按厂家兼容规则完成更新。
- 所有命令、应答、文件、版本、分区地址和失败阶段都有日志。
- 升级完成后 `ATI` 或 `AT+CGMR` 查询版本正确。
- 普通 NTN AT 透传功能恢复正常。
- 断线、超时、包损坏不会被错误地报告为升级成功。

## 1. 执行摘要与总体结论

Step2 是本项目串口升级工作的关键进展。员工3已经把原先基于 MCDTV5.exe 反汇编得到的协议推测，推进到四份真实 Bus Hound 6.00 抓包的字节流重组与目标文件比对。审查结果认为：

1. **协议主干已基本明确**：BootROM 握手、QSPI 初始化、清写保护、改速、擦除、固定/变长写、NV 页写、读页和分区表提交均有真实抓包依据。
2. **NV CA034 黄金样本已得到强证据**：423B 有效数据、512B 双页数据、主备区内容及 SHA-256 与员工3 V2.0 编译器输出一致。
3. **分区表最重要的防变砖规则成立**：四次下载的分区表演变中，报告记录的唯一差异均为 `0xE8..0xEB` 的 stamp；`firmware.mv_length=0x80000`、`dsp0_code.mv_length=0`、`sec_mv_length=0x2000` 必须保留。
4. **不能把“发送数据与目标文件一致”写成“模组 Flash 全量读回一致”**：当前审计脚本比较的是 Bus Hound 捕获到的主机 TX 写入载荷与目标文件；抓包中每个组件只看到一次 `0xEB` 地址 0 的 256B 分区表读取，没有看到 E31/DSP/Boot 全镜像逐页读回。因此，当前证据证明了“主机发送字节流正确”，尚未证明“模组 Flash 写后全量读回正确”。
5. **员工3正式实现方案方向正确，但有必须先修正的设计细节**：元数据结构体实际只有 252B；首扇区完整备份空间不足；NUPG 帧开销描述不一致；4KiB/16KiB 的 `0x7A` 分块和物理 30ms/改速时序尚未实测。
6. **MCU 源码风险复核成立**：当前启动顺序可能在读取 NTN 安装状态前正常上电模组；主 MCU OTA 未确认存在 60s 强制复位；NTN UART3 只有一个 RX 线程，且该线程当前会继续执行 AT/URC/RAW 分发；USART 驱动只检查 TX_EMPTY，RX 错误标志被清除但没有累计错误计数。

**员工2结论：建议将员工3 V2.0 作为“协议字节层开发基线”，不建议将其标记为“正式产品升级已验证”或“量产可放行”。先修正本报告第 6 节问题，再按第 8 节 M0→M3 顺序推进。**

员工3通过每次下载前 `0xEB` 读出的 256B 分区表 SHA-256，与本次 `0x32` 发出的 256B 分区表 SHA-256 建立链式关系：

| E31 | `45816274bc518b67` | `40dcffcd9d9dca50` | `0x6AD6D2C7 → 0x6B0AD553` |
| DSP | `40dcffcd9d9dca50` | `947200362c8429e6` | `0x6B0AD553 → 0x6B0AD649` |

该哈希链强力支持四次抓包按 E31→DSP→NV→二级 Boot 顺序在同一设备状态上连续完成。但它仍然是分区表状态连续性证据，不是设备序列号级的唯一身份认证。

### 2.4 抓包启动横幅差异

审计 JSON 中：
- DSP、NV、二级 Boot 的首个未请求 IN 数据包含 `\nVER:B5.0\n`；
- E31 的首个未请求 IN 数据为 109 个 `0x55`，`banner_present=false`，未捕获到版本横幅。

因此，正式状态机必须把版本横幅视为**可选信息**，不能要求每次上电都必须先收到横幅；同步条件应以可识别的连续 `0x55`、超时和后续 `C0 3F` 响应共同判定。E31 横幅缺失的原因需要保留为抓包边界/启动时序待核查项，不能据此认定 E31 启动时没有横幅。

## 3. 协议字节层复核结论

通用规则：
- 串口：8N1、无硬件流控；上电初始 115200 bps。
- 命令地址和变长长度：BE32。
- 分区表与 NV 内部整数字段：LE。
- 命令校验：初值 `0xFF`，从 opcode 到 payload 末尾逐字节 XOR。
- 除 `0x57` 的 ASCII 回显外，协议主体是二进制流，不得按 AT 行、CR/LF 或空闲间隔随意拆帧。

| 指令 | 主机 TX | 抓包所见 RX | 员工2结论 / 实现约束 |
|---|---|---|---|
| BootROM 同步 | 先设置 BOOTSEL 并复位；模组主动吐数据 | 版本横幅（部分抓包出现）及连续 `0x55` | 横幅可选；应容忍启动横幅与 U 字节分段到达 |
| `C0` | `C0 3F` | `05 00` | 响应为精确 2B；应加入脚本断言和 MCU 超时/版本检查 |
| `46` | `46 B9` | `06` | 初始化 QSPI 后才允许后续写保护寄存器操作 |
| `57` | 两条 10B 帧：`57 56 80 00 18 06 00 00 01 61`、`57 56 80 00 24 00 00 02 00 58` | 每条报告为 24B：23B ASCII 回显 + 尾字节 `F9` | 必须收满并校验完整回显与 `F9`，不可用“收到2字节”或单字节 ACK 判成功 |
| `55` | `55 AA` | `06` | 改速前置时钟配置 |
| `50` | `50 09 A6`（1.5M）、`50 04 AB`（115200） | `06` | 抓包只证明这两档实际使用；921600/460800 不是本轮抓包已验证档位 |
| `20` / `D8` | 6B 命令，地址 BE32 | `06` | 分别按 4KiB / 64KiB 对齐；混合擦除地址范围必须按目标 profile 计算 |
| `79` | 5B 头，后接 65,536B 数据和 1B CHK | `06` | 实测用于完整 64KiB 块；CHK 覆盖头和数据。30ms 精确物理间隔仍须逻辑分析仪确认 |
| `7A` | 9B 头（地址+长度均 BE32），后接 LEN 数据和 1B CHK | `06` | 实测尾块长度为 57,086 / 8,983 / 18,903B；4KiB/16KiB 小块策略尚未被本轮抓包证明 |
| `02` | `02 + BE32 地址 + 256B + CHK`，总 262B 单包 | `06` | NV 主/备各两页；不得套用 `79/7A` 的头尾拆分方式 |
| `EB` | `EB + BE32 地址 + CHK`，总 6B | 纯 256B 数据 | 本轮每份抓包只看到地址 0 的 256B 分区表页读取；尚未验证全镜像、非零地址和连续多页读取 |
| `32` | `32 + BE32 地址 + 256B + CHK`，总 262B 单包 | `06` | 写入地址 0 的分区表页；只允许按经核验的分区表模板生成 |

收尾顺序：`55 AA → 06`，`50 04 AB → 06`，释放 BOOTSEL 并通过硬件复位恢复正常启动。四份抓包未观察到 `B0 4F`，不应在没有新证据时额外加入该命令。

### 3.1 两项需要严格区分的“已知”与“未测”

1. **改速 ACK 相位未冻结**：Bus Hound 文件未开启可用于微秒级相位判定的时间戳；不能仅凭 TX/RX 字节顺序判断 `0x50` 的 `0x06` 是旧速还是新速发出，也不能确定模组何时真正切换波特率。
2. **30ms 是静态工具路径/实现依据，不是本轮 Bus Hound 的物理测量结果**：报告中的 30ms 可以作为初始实现参数，但最终必须测量从最后一个停止位到下一段数据起始位的真实间隔和容差。

## 4. 分区表规则复核：最高等级防变砖约束

### 4.1 必须保留的字段

员工3对 ST1000 / PRODUCT=4 / VER=100 的 256B `T_Header_5gNew` 分区表解剖，结合四次下载前后数据，得到以下关键规则：

| 字段 | 偏移 | 抓包/配置值 | 员工2结论 |
|---|---:|---:|---|
| `sec_addr` | `0x0C` | `0x00008000` | 保留 |
| `sec_mv_length` | `0x10` | `0x00002000` | 保留，不能写成二级 Boot 文件长度 |
| `firmware.off/size` | `0x70/0x74` | `0x00028000 / 0x00380000` | 保留 |
| `firmware.mv_length` | `0x78` | **`0x00080000`** | **严禁改成 E31 文件长度 `0x2649D7`** |
| `dsp0_code.mv_length` | `0x84` | **`0x00000000`** | 保留，不能改为 DSP BIN 文件长度 |
| `rfe_nv.mv` | `0x60`附近字段 | `0x0713C398` | 出厂射频校准/校验相关值，禁止重建或覆盖 |
| `cfg_nv` | `0xC4` | `0x004C4000 / 0x3000` | 主区 `0x4C4000`，备区按 `+0x2000` |
| `file_system` | `0xDC` | `0x004D0000 / 0x00300000` | LittleFS 区域，禁止误擦 |
| `stamp` | `0xE8..0xEB` | 每次更新变化 | 四次抓包中唯一变化的 4B 字段 |

### 4.2 正式版封口算法

1. 进入 ROM 后先读取分区表页 `0x00000000`，校验 magic、version、product、board、Flash size 和关键分区边界。
2. **还必须读取并保存首个 4KiB 扇区的全部 16 页**（`0x00000000..0x00000FFF`），确认其余 15 页是否全为 `0xFF`；如存在非 `0xFF` 数据，必须完整备份。
3. 以真实读回的 256B 表为唯一基底，仅更新 `0xE8..0xEB` stamp，其余 252B 不允许变化。
4. 擦除首扇区，写入 256B 表页，再读回 256B 逐字节比较。
5. 在完成全流程前，必须保留可恢复的原始 4KiB 扇区备份；不能只备份 256B 表页却假定其余 15 页为空。

**证据边界**：本轮抓包实际展示的是地址 0 的 256B 读取和 4KiB 扇区擦除，并没有展示其余 15 页的读取。因此，“其余页面为空”目前不是已验证事实。

## 5. NV 黄金样本复核

员工3 V2.0 的 NV 编译器对 CA034 XML 得到：
- XML：15,841B；
- 有效二进制：423B；
- 页填充：89B `0x00`；
- 双页总长：512B；
- `PageCRC` 位于偏移 `0x1A6`，实测值 `0x32`；
- `Pageflag` 位于 `0x008..0x00B`，实测 LE32 为 `0x7FFFFFFF`；
- 主区地址：`0x4C4000`、`0x4C4100`；
- 备区地址：`0x4C6000`、`0x4C6100`；
- 主备 512B 相同，且与 `compile_nv_xml_v2.py` 输出一致。

### 5.1 差异根因

XML 的 `Pageflag=4294967055 (0xFFFFFF0F)` 在线上成为 `FF FF FF 7F`（`0x7FFFFFFF`）。员工3结合 MCDTV5.exe 反汇编认为，Windows x64 LLP64 下的 32 位有符号 `long` `strtol()` 对超出 `LONG_MAX` 的值饱和到 `0x7FFFFFFF`。在此线上数据基础上重算 XOR，`PageCRC=0x32`。

### 5.2 员工2的使用约束

1. CA034 的 512B SHA-256 可以作为黄金向量；每次升级 NV XML、固件版本或模组型号变化，都必须重新生成并与原厂短 NV 抓包比对。
2. `mcdt_compat` 是为了兼容原厂工具行为，不代表该截断行为是理想数据格式；编译器必须输出明确告警，禁止把饱和截断隐藏起来。
3. 未经批准不得把 `strict_u32` 输出直接烧录到设备；它与原厂 MCDT 兼容模式可能不同。
4. NV 写入前先备份设备原 NV；现场设备专属字段（APN、频段、校准或其他参数）需要产品定义“保留/覆盖”策略，不能默认用工厂黄金值覆盖所有在用设备。

## 6. 员工3正式实现方案的独立审查与必须修正项

### 6.1 可采纳的总体架构

建议保留员工3提出的三种显式模式：

- `STAGED_FULL`：V30 8MiB NOR 主路径，PC 经 RS232 把完整发布包上传到 MCU/NOR；缓存全量读回 SHA-256 通过后才进入安装阶段。PC 收包中断时不应触碰模组。
- `STREAM_4K`：旧版 2MiB 或 NOR 故障时显式选择的在线流式路径；每个块必须先在 MCU RAM 收齐并校验，再转发给 MS150。不得静默降级。
- `PASSTHROUGH_115200`：工厂/研发救援路径，MCU 受控桥接原厂工具；应有专用权限/状态保护，避免正常业务状态误进入透明下载。

V30 实机容量记录为 BY25Q64ES (SFDP)、JEDEC `68 40 17`、8MiB、4KiB Sector；现有 NTN 可用 reserved 范围为 `[0x212000, 0x800000)`。员工3提出的五段分区总长度计算正确：

| 分区 | 起始 | 长度 | 结束（不含） |
|---|---:|---:|---:|
| `ntn_meta_a` | `0x212000` | `0x001000` | `0x213000` |
| `ntn_meta_b` | `0x213000` | `0x001000` | `0x214000` |
| `ntn_fw_cache` | `0x214000` | `0x2FF000` | `0x513000` |
| `ntn_nv_work` | `0x513000` | `0x001000` | `0x514000` |
| `ntn_spare` | `0x514000` | `0x2EC000` | `0x800000` |

五段合计 `0x5EE000`，与原 reserved 长度相同；CA034 四个原始组件按 4KiB 对齐合计 2,727,936B，3,141,632B 的缓存区理论剩余 413,696B。修改 FAL 时必须删除原可写 `reserved` 父分区，禁止父子分区重叠；同时核对 OTA_APP/OTA_BL2 与非 OTA 构建的所有条件分支。

### 6.2 P0 设计缺陷：元数据结构体不是 256B

员工3方案中的 `ntn_meta_record_t` 使用 `#pragma pack(1)`，按字段长度实际计算：

`32B header + 176B comp[4] + 8B manifest + 4B last_error + 24B rsvd + 4B CRC + 4B commit = 252B`

因此文档注释中的“精确 256 字节”不成立，且 CRC/commit 偏移与注释的 `CRC32(offset 0..247)` 不匹配。

**修正建议：**
- 将 `rsvd[24]` 改为 `rsvd[28]`，使结构体达到 256B；
- 用 `_Static_assert(sizeof(ntn_meta_record_t) == 256, "...")` 在编译期强制校验；
- 明确 CRC 字段位于 offset 248，commit_word 位于 offset 252；
- 写入时先写 offset 0..251 并读回，再单独写 offset 252 的 commit word 并读回；
- 双扇区日志扫描必须校验 magic/schema/generation/CRC/commit，不能只根据 state 字段判有效。

### 6.3 P0 设计缺陷：原始分区表扇区备份空间未闭合

协议报告要求擦除首个 4KiB 扇区前读取 16 页并保留非 `0xFF` 数据；正式实现方案和 `ntn_nv_work=4KiB` 却主要描述 256B 表头快照、512B 黄金 NV 和 NV 备份工作区。一个 4KiB 分区无法同时保存完整 4KiB 首扇区、512B 黄金 NV 和 512B 原 NV 备份。

**修正建议：**
- 从 `ntn_spare` 划出独立 `ntn_table_backup`（至少 4KiB，建议按擦除粒度/版本化记录设计）；
- `ntn_nv_work` 保留给黄金 NV、原 NV 备份及 NV 安装状态；
- 在真正擦除 `0x00000000` 前，对 16 页完成读取、SHA-256、持久化和读回验证；
- 若原厂测试证明其余 15 页恒为 `0xFF`，仍应把该结论固化为板卡/BootROM 版本约束和验收用例，而不是依赖默认假设。

### 6.4 P0 规范缺口：NUPG 帧开销描述不一致

正式方案第 5 节称 NUPG 固定开销 22B、payload 最大 1020B；第 4.1 时序图却写成“每块 4×1020B + 16B NUPG 帧”。这两处不能同时作为精确协议规范。

在编码前必须单独冻结：
- 固定头每个字段的 offset、宽度、字节序；
- header 长度、CRC32 长度及其覆盖范围；
- `payload_len` 最大值、零长度帧规则；
- session_id、seq 的回绕/重置规则；
- BEGIN/BLOCK_BEGIN/BLOCK_DATA/BLOCK_COMMIT/FINISH/INSTALL/STATUS 的完整帧类型；
- ACK/NACK、超时、重传、重复帧幂等和冲突处理；
- 4KiB NOR 写块如何映射为若干 NUPG 数据帧，以及最后不足 1020B 的分片规则。

在上述规范冻结前，不应让 PC 与 MCU 两端分别按图示猜测实现。

### 6.5 物理和协议验证缺口

| 项目 | 当前证据 | 仍需完成 |
|---|---|---|
| `0x57` | 员工3报告记录 24B 回显 + `F9` | 解析脚本要对所有 10 次寄存器写响应逐次断言，不应只保存前两条 sample |
| `C0 3F` | JSON 记录四次均为 `05 00` | 在解析脚本中加入精确 2B 响应断言 |

### 6.6 MCU 当前源码风险复核

源码基线为 `work_v1_boot_fix @ 03b0abc3f4062178c1d5864100bdc98e9c87b905`。员工3提出的以下风险可在该基线源码中定位：

1. **模组启动早于 NOR 状态检查**  
   `hw_power_init()` 使用 `INIT_PREV_EXPORT`，初始化时会调用 `hw_power_ntn_set(RT_TRUE)`；该函数将 BOOT 引脚 PA10 拉低并按正常模式给模组上电。另一方面，`app_flash_init()` 使用 `INIT_DEVICE_EXPORT`。因此必须把“首次 NTN 正常上电”从早期 GPIO 初始化中拆出，等 Flash 探测、元数据扫描和恢复策略判定后再执行。  
   源码：`applications/hw_power.c`、`applications/app_flash.c`。

2. **主 MCU OTA 未确认时的 60 秒复位**  
   `main.c` 在启动约 6 秒后尝试确认 MCU OTA；若到 60 秒仍未确认则执行 `rt_hw_cpu_reset()`。NTN 安装可能超过 60 秒，因此升级入口必须拒绝未确认的 MCU OTA 镜像，并在 NTN 安装期间确保不会被该保护逻辑意外复位。  
   源码：`applications/main.c`。

3. **UART3 唯一读者与数据分发**  
   当前 `ntn_rx_thread_entry()` 是 UART3 的读线程；每次读到字节后会依次调用 `ntn_command_receive()`、`ntn_rx_line_feed()`、RAW handler 和透明桥接逻辑。升级态必须在这些解析/分发动作之前进行 owner 判断，将原始字节交给升级状态机；不得再创建第二个线程同时读取同一 UART。  
   源码：`applications/ntn_ms150.c`。

4. **TX_CPLT 与 RX 错误计数**  
   当前 HC32 `hc32_putc()` 轮询的是 `USART_FLAG_TX_EMPTY`，不等于移位寄存器最后一位已发出；RX 错误处理函数读取数据并清除 ORE/PARITY/FRAME 标志，但没有将错误计数暴露给上层。正式升级需要新增可超时的 TX_CPLT 等待、ORE/FE/PE 计数及单块错误判废机制。  
   源码：`bsp/hc32/libraries/hc32_drivers/drv_usart.c`。

5. **FAL 容量强检尚未实现**  
   当前 `app_flash_init()` 会探测 Flash、输出容量信息并执行 `fal_init()`，但未遍历 NTN 分区最大结束地址与 SFDP 实际容量做运行时边界强校验。正式启用 NTN 暂存前必须增加 JEDEC/SFDP/擦除粒度白名单和最大分区结束地址检查；2MiB 器件必须拒绝 `STAGED_FULL`。

## 7. 对员工3 V2.0 报告的修订建议

员工3的协议报告和实现方案整体方向可采纳，但建议在 V2.1 或勘误页中修订以下措辞：

1. 把“4组件 100% 字节级一致”明确改成“Bus Hound 捕获的主机 TX 写入载荷与四个目标文件 100% 一致”；只有完成写后 `0xEB` 全量读回，才能写“模组 Flash 全量读回一致”。
2. 把“全部命令应答自动审计 PASS”改成更精确的口径：当前脚本已对若干命令 ACK、XOR 和载荷做自动检查；`0x57` 与 `C0` 响应还需增加显式断言。
3. 把 `0xEB` 结论限定为“地址 0 的 256B 分区表页读取已捕获”；非零地址与镜像全量读取待测。
4. 把 `0x7A` 的 4KiB/16KiB 分块标注为 MCU 设计候选，不标注为原厂已实测支持。
5. 把 30ms、`0x50` ACK 速率相位和 1.5Mbps 板内链路标注为物理层门禁，不作为已冻结参数。
6. E31 的启动横幅未出现在当前抓包中，启动横幅应标为可选。
7. 将 `ntn_meta_record_t`、首扇区备份空间和 NUPG 帧长度规范作为正式编码前必须关闭的设计问题。
